핵심 요구사항 21개 구현 / 정산은 금액 표시까지

근거: 프로젝트 요약본 · 상세는 발표자 노트

다음 장 연결: “이 흐름을 세 사람이 나눠 맡았고, 쓰는 AI도 같지는 않았습니다.”

  • 20초: 같은 파일의 동시 수정 충돌을 피하려 겸상 상세를 기능별 섹션으로 나눴다(#39). 그 구조에서 여러 섹션이 참여 여부 같은 데이터를 각각 조회했다. 참여 직후 공지 띠가 나타나지 않는 불일치가 생겼다.
  • 20초: 참여 섹션에서 행동이 성공해도, 공지 섹션이 별도로 읽은 참여 여부까지 함께 갱신되는 구조는 아니었다. 각 기능의 성공과 화면 전체 상태의 일치가 연결되지 않았다.
  • 20초: #75에서 여러 섹션이 공유하는 데이터는 상위 페이지에서 조회·전달하고, 이를 바꾸는 행동 뒤에는 부모에서 다시 조회하도록 결정했다. 통합 담당이 통합 PR에서 반영했다. 섹션 전용 데이터는 해당 섹션이 계속 맡았다.
  • 10초: 다른 사용자의 변경을 받는 실시간 구독은 이후 별도로 반영했다. #75에서 실시간 구독까지 함께 확정한 것으로 설명하지 않는다.

다음 장 연결: “공유 데이터를 맞춘 뒤에도, 다른 사람이 바꾼 메뉴까지 들어오게 하려면 확인할 연결이 더 있었습니다.”

개선 제안화면 × 테이블 대조

늦은 응답이 최신 상태를 덮음모의 테스트로 응답 순서 제어
재연결 중 변경 누락실제 Supabase에서도 재현·수정 확인
근거: #5 · #100 · #102 · #116 · 상세는 발표자 노트
  • 15초: 도입의 사건으로 돌아온다. #5로 같은 기능의 문서·코드 검토자는 정했지만, 실시간 구독을 정한 문서 자체에서 메뉴 테이블이 빠졌다. 작성 쪽 에이전트도 문서의 테이블을 기준으로 구현했다.
  • 20초: 담당 화면, 응답 순서 등 구현 품질, 문서와 구현 일치의 세 관점으로 검토했으나, 화면에 필요한 데이터 전체가 구독 대상에 있는지는 대조하지 않았다(#100). 문서와 코드의 일치만으로 문서의 누락까지 잡지는 못했다.
  • 20초: Host 취합 현황에서 다른 참여자의 메뉴 변경이 반영되지 않는 현상을 확인했고, #101 결정 후 #102에서 메뉴 구독을 추가했다. 화면 × 테이블 대조는 개선 제안이며 효과를 검증한 결과는 없다.
  • 25초: 같은 교차 검토에서 응답 순서와 재연결 결함은 찾아 재현했다. 응답 순서는 모의 테스트로 제어했고, 재연결은 실제 Supabase에서도 확인했다. 맡긴 범위에서는 항상 정확하다는 결론 대신 실제 확인한 두 사례로 효용을 설명한다.
  • 10초: “구체적인 결함을 재현한 검토에서도, 무엇을 빠뜨렸는지 확인하는 관점은 별도로 필요했습니다.”

다음 장 연결: “데이터 연결에서 빠진 확인이 있었다면, PR을 합치는 순서에서도 빠진 확인이 있었습니다.”

  • 20초: 규칙 파일이 비대해지지 않도록 결정과 이유는 decision에, 관찰과 개선 제안은 retro에 남겼다. 표는 발표를 위해 기록을 다시 정리한 것이며 당시 사용한 추적표가 아니다.
  • 30초: 섹션 분리는 유지하면서 공유 데이터 조회를 통합했고, 검토에서 빠진 메뉴 구독은 추가했다. 의존성 사례는 선행 조건이 개별 PR에 적혀 있었어도 확인 절차에서 놓친 문제다. 조건 자체가 없었다고 설명하지 않는다.
  • 15초: 하단 요청은 #100·#88의 제안을 풀어 쓴 예시다. 두 회고는 공통 규칙으로 추가하지 않고 관찰 기록으로 종료했으며, 이 요청 방식의 효과도 아직 검증하지 않았다. 머지 차단 사항과 후속 통합 작업을 구분해 달라는 요청도 필요에 따라 덧붙일 수 있다.
