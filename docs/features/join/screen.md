## 1. 화면 범위와 진입

겸상 상세 안에 참여·내 메뉴 영역을 두고, Host에게 취합 현황 영역을 추가하는 구성을 제안한다. 아래 화면 ID는 설계 영역의 식별자이며 별도 URL을 뜻하지 않는다.

| 화면 ID | 영역 | 대상 | 요구사항 |
|---|---|---|---|
| SCR-JOIN-01 | 참여 상태·참여하기 | 로그인 사용자 | REQ-JOIN-01 |
| SCR-JOIN-02 | 내 메뉴·부담액·주문 확정·참여 취소 | 해당 겸상의 참여자 (Host 포함) | REQ-JOIN-02~04 |
| SCR-JOIN-03 | 참여자별 취합·확정 현황 | 해당 겸상의 현재 Host | REQ-JOIN-05 |

- 겸상 목록에서 선택한 겸상의 상세로 진입하는 흐름을 제안한다.
- 상세 상단에는 제목, 유형, 겸상 상태, 현재 인원/정원, 주문 예정 시간을 표시한다. 가게 메뉴판 링크는 값이 있을 때 표시한다. 집합/수령 장소는 값이 없어도 `아직 정하지 않았습니다`를 표시한다(`docs/features/notice/screen.md` SCR-NOTICE-03).
- 메뉴판 링크와 장소 표시는 각각 `docs/features/meal/requirements.md` REQ-MEAL-03, `docs/features/notice/requirements.md` REQ-NOTICE-02와 연결되는 공통 상세 영역이다.
- 인증·겸상 생성·Host 넘기기·공지·주문완료·정산 기능의 화면 동작은 각 담당 기능 문서를 따른다.
- 상세 경로는 `/meals/:mealId`이며 `src/shared/MealDetailPage.tsx`가 `NoticeSection` → `MealInfoSection` → `JoinSection` → `SettleSection` 순서로 조립한다. join 영역은 `src/features/join/JoinSection.tsx`에서 구현하고 `useParams()`의 `mealId`를 사용한다. 경로·섹션 분리 근거: 결정 #39 및 PR #35. 공지 최상단 배치는 `docs/features/notice/screen.md` SCR-NOTICE-01과 PR #61을 따른다. 문서의 `/meals/:id`는 같은 상세 경로를 뜻하며 실제 라우트 매개변수 이름은 `mealId`다.
- 겸상 기본 정보·Host 관리 영역은 meal 담당, 참여·메뉴·취합 현황은 join 담당, 공지·장소는 notice 담당, 주문완료·정산은 settle 담당 범위다. 상단 표시 항목의 구체적 배치는 meal 화면 설계에서 정하며 join에서 중복 구현하지 않는다.
- 모집중 목록에서 사라진 겸상의 재진입은 #70의 내 겸상 목록에서 제공하는 방향으로 합의했다. join 전용 진입 화면은 추가하지 않는다. 목록 변경은 통합 담당의 기획서 반영 후 meal 담당이 구현하며, join 구현의 선행 조건이 아니다. 자동 제외된 사용자는 참여 행이 삭제되어 내 겸상 대상에서도 제외되며 별도 재진입 경로를 추가하지 않는다.

## 2. 기본 배치

모바일과 데스크톱 모두 단일 열을 기본으로 한다. Host도 본인 메뉴를 입력하므로 내 메뉴 아래에 취합 현황을 배치한다.

```text
공지 띠 (참여자에게 표시, notice 담당)
겸상 제목                   [식사/배달] [모집중]
현재 인원 / 정원            주문 예정 시간
메뉴판 링크 (입력된 경우)
집합/수령 장소 (미입력 시 아직 정하지 않았습니다)
─────────────────────────────────────────────
SCR-JOIN-01 참여 상태
미참여: [참여하기] 또는 정원 마감 안내
참여중: 참여중 안내
─────────────────────────────────────────────
SCR-JOIN-02 내 메뉴 (참여자에게 표시)
내 주문 상태: 미확정 / 확정됨
메뉴명 [                  ]
금액   [                  ] 원
[메뉴 추가]

메뉴명                  9,000원 [수정] [삭제]
메뉴명                  3,000원 [수정] [삭제]
내 부담액                          12,000원
주문 확정·자동 잠금 안내
[주문 확정]
[참여 취소]
─────────────────────────────────────────────
SCR-JOIN-03 취합 현황 (Host에게만 표시)
참여자 이름 · 이메일              [확정/미확정]
메뉴명 · 금액 / 참여자 부담액
… 참여자별 반복 …
전체 합계                          36,000원
```

- 수치와 메뉴는 배치 설명용 예시다.
- 48em 미만은 좌우 여백 16px, 이상은 24px로 한다. 본문 최대 너비는 960px, 입력 폼 최대 너비는 560px로 한다.
- 긴 메뉴명과 이메일은 줄바꿈하고, 금액과 행동 버튼이 화면 밖으로 밀리지 않게 배치한다.
- 주요 행동은 채움형 버튼, 수정 등 보조 행동은 외곽선·연한 배경, 삭제·참여 취소는 위험 행동 문구와 색으로 구분한다.
- 금액은 `12,000원` 형식으로 표시하고 합계를 강조한다. 색·간격·글자 크기는 공통 디자인을 따른다.

## 3. SCR-JOIN-01 참여 상태

| 조건 | 표시와 행동 |
|---|---|
| 모집중·주문 예정 시간 전·미참여·정원 여유 | 현재 인원/정원과 `참여하기` 표시 |
| 모집중·주문 예정 시간 전·미참여·정원 가득 참 | `정원이 가득 찼습니다`와 비활성 참여 버튼 표시 |
| 이미 참여중 | `참여중` 표시, 중복 참여 버튼 대신 SCR-JOIN-02 표시 |
| 모집중이나 주문 예정 시간 도달 | 참여 버튼 비활성, `주문 예정 시간이 되어 참여할 수 없습니다` 표시 |
| 주문중·주문완료·정산 | 참여 버튼 비활성, `모집이 마감되어 참여할 수 없습니다` 표시 |
| 취소 | 참여 버튼 비활성, `취소된 겸상입니다` 표시 |

- 참여 성공 후 현재 인원과 본인의 참여 상태를 갱신하고 같은 상세에서 SCR-JOIN-02를 표시한다.
- 마지막 한 자리에 동시 참여한 경우 서버 처리 결과에 따라 성공 또는 정원 마감 안내를 표시한다. 화면에 보였던 잔여 자리만으로 성공 처리하지 않는다.
- 중복 참여 응답 시 중복 행을 만들거나 인원을 더하지 않고 실제 참여 상태를 다시 반영한다.
- 다른 참여자의 취소로 자리가 생긴 상태를 조회하면 다시 참여할 수 있게 표시한다.

## 4. SCR-JOIN-02 내 메뉴와 주문 확정

### 입력·수정·삭제

- 메뉴명과 금액 입력창에는 항상 라벨을 표시한다. 메뉴는 한 항목씩 추가하며 여러 항목을 허용한다.
- 금액이 비었거나 정수가 아니면 저장하지 않고 금액 아래에 `금액을 원 단위 정수로 입력해 주세요`를 표시한다.
- DB 문서의 `order_items.name`은 공백만으로 저장할 수 없고 `price`는 0 이상의 정수다. 공백뿐인 메뉴명과 음수 금액은 저장하지 않고 해당 입력창 아래에 안내한다. 근거: `docs/common/db-schema.md`의 `order_items`, `docs/common/design-system.md` §5 입력 오류.
- 저장된 각 항목에 `수정`·`삭제`를 둔다. 수정은 해당 항목을 입력창으로 전환하고 `저장`·`수정 취소`를 표시하는 방식을 제안한다. 수정 취소는 저장 전 입력만 되돌린다.
- 메뉴 삭제는 추가 확인 대화상자 없이 바로 삭제를 요청한다. 처리중에는 중복 요청을 막고, 실패 시 삭제 성공으로 표시하지 않는다.
- 저장된 메뉴 금액의 합을 `내 부담액`으로 표시한다. 입력 중인 미저장 금액은 합계에 포함하지 않는다.
- 메뉴가 없으면 `아직 입력한 메뉴가 없습니다`와 `내 부담액 0원`을 표시한다.
- 모집중이고 주문 예정 시간 전이며 메뉴가 없는 일반 참여자에게는 SCR-JOIN-02 내 메뉴 영역에 `주문 예정 시간까지 메뉴를 입력하지 않으면 참여자에서 제외됩니다`를 함께 표시한다. Host에게는 이 사전 경고를 표시하지 않는다. 메뉴 저장 후에는 경고를 숨기고, 마지막 메뉴를 삭제해 다시 조건을 충족하면 표시한다. 근거: `docs/common/planning.md` §3 주문중 전환·Host 참여.

### 개인 확정과 겸상 잠금

| 겸상 상태·본인 상태 | 메뉴 추가·수정·삭제 | 주문 확정 | 참여 취소 | 안내 |
|---|---|---|---|---|
| 모집중·주문 예정 시간 전·미확정 | 가능 | 메뉴 1개 이상이면 가능 | 일반 참여자는 가능, Host는 불가 | 미확정이며 주문 예정 시간 전인 동안 변경 가능 |
| 모집중·확정됨 | 불가 | 확정됨 표시 | 불가 | 주문 확정 후에는 메뉴 변경과 참여 취소를 할 수 없습니다 |
| 모집중이나 주문 예정 시간 도달 | 불가 | 비활성 | 불가 | 주문 예정 시간이 되어 메뉴와 참여가 잠겼습니다 |
| 주문중 | 불가 | 비활성 | 불가 | 주문 예정 시간이 되어 메뉴와 참여가 잠겼습니다 |
| 주문완료·정산 | 불가 | 비활성 | 불가 | 주문이 마감되어 변경할 수 없습니다 |
| 취소 | 불가 | 비활성 | 불가 | 취소된 겸상입니다 |

- 확정 버튼 근처에 `주문 확정은 선택입니다. 확정하면 메뉴와 참여가 잠깁니다. 확정하지 않아도 주문 예정 시간이 되면 자동으로 잠깁니다`를 표시한다.
- 메뉴가 없는 상태에서 확정을 시도하면 저장하지 않고 `메뉴를 하나 이상 입력해 주세요`를 표시한다.
- 주문 확정은 추가 확인 대화상자 없이 버튼 1탭으로 요청한다. 근거: `docs/common/planning.md` §3 주문 확정.
- 확정 성공 후 개인 상태를 `확정됨`으로 표시한다. 확정 시각은 서버에 기록하며 별도 취소·확정 해제 동작은 제공하지 않는다.
- **겸상의 주문중 상태와 개인의 확정 여부는 별도다.** 자동 잠금만으로 미확정 참여자를 확정됨으로 표시하거나 확정 시각을 생성하지 않는다.
- 자동 전환 때 메뉴가 없는 일반 참여자는 제외되고, Host는 메뉴가 없어도 남는다. 메뉴가 있는 참여자는 미확정이어도 포함된다. 남은 메뉴 항목이 하나도 없으면 주문중 대신 취소로 전환한다. 실제 전환과 제외 처리는 `docs/features/settle/requirements.md` REQ-SETTLE-04의 책임이다.
- 최신 조회에서 자동 제외 등으로 비참여 상태가 확인되면 같은 상세에 머물며 SCR-JOIN-02를 숨기고 SCR-JOIN-01의 일반 모집 마감 안내를 표시한다. 주문중·주문완료·정산은 `모집이 마감되어 참여할 수 없습니다`, 취소 상태는 `취소된 겸상입니다`를 표시한다. 제외 이력 스키마나 별도 자동 제외 사유 안내는 추가하지 않는다. 상태 조회·갱신의 구현 범위는 §6을 따른다.

### 참여 취소·재참여

- Host는 일반 참여 취소가 불가하며, `Host는 참여를 취소할 수 없습니다. Host 넘기기 또는 겸상 취소를 이용해 주세요`를 안내한다. Host 관리 동작은 meal 담당 영역에서 제공한다.
- 참여 취소 근처에 `참여를 취소하면 입력한 메뉴도 삭제됩니다`를 표시한다.
- 취소 성공 후 SCR-JOIN-02 대신 SCR-JOIN-01을 표시하고 현재 인원을 갱신한다.
- 모집중이고 주문 예정 시간 전이며 정원에 여유가 있으면 다시 참여할 수 있다. 재참여 후 메뉴 목록은 빈 상태, 부담액은 0원으로 표시한다.
- 참여 취소에만 확인 대화상자를 표시한다. 제목은 `참여 취소`, 안내는 `참여를 취소하면 입력한 메뉴도 삭제됩니다`, 버튼은 보조 행동 `돌아가기`와 위험 행동 `참여 취소`로 구성한다.
- 확인 대화상자의 `참여 취소`를 선택해야 취소 요청을 보낸다. `돌아가기`·바깥 누르기·Esc로 닫으면 참여와 메뉴를 유지한다. 요청 처리중에는 로딩과 중복 제출 방지를 적용하고, 실패 시 대화상자에 안내하며 취소 성공으로 처리하지 않는다.
- 메뉴 삭제는 즉시 요청하고 주문 확정은 기획서의 1탭 기준을 유지한다.

## 5. SCR-JOIN-03 Host 취합·확정 현황

- 현재 Host에게만 표시한다. 참여자별 카드에 이름(본명), 이메일, 확정/미확정, 메뉴명·금액, 부담액을 표시하고 마지막에 전체 합계를 둔다.
- 메뉴가 없는 참여자는 `메뉴 미입력`, 부담액 `0원`, 개인 상태 `미확정`으로 표시한다. 자동 제외가 처리된 후에는 현재 참여자 목록을 반영한다.
- Host 자신의 메뉴도 참여자 현황과 전체 합계에 포함한다.
- 자동 제외 등으로 참여자가 아니게 된 사용자는 SCR-JOIN-02를 볼 수 없으며 메뉴 조회 권한도 없다. `docs/common/db-schema.md` §5에서 `meals`·`meal_members` 조회는 로그인 사용자 전체에 허용하지만 `order_items`는 해당 Host·참여자만 조회할 수 있다. 공지와 정산 표시도 각 기능의 참여자 제한을 따른다. 별도의 제외 이력·알림은 임의로 추가하지 않는다.
- 일반 참여자에게 다른 참여자의 이메일을 표시하지 않는다. 이메일은 `get_meal_member_emails`의 Host 권한을 전제로 조회한다.
- 이 영역은 조회용이다. 타인의 메뉴 수정·확정이나 주문완료 전환 버튼은 join의 기능으로 추가하지 않는다.
- 이메일 조회 등 일부 데이터가 실패하면 해당 실패를 표시하며, 조회 실패를 빈 메뉴나 0원으로 대체하지 않는다.

## 6. 로딩·오류·동시 변경

| 상황 | 화면 처리 제안 |
|---|---|
| 최초 조회중 | 로딩 표시. 참여 여부·권한·상태가 확인되기 전 행동 버튼 비활성 |
| 저장·참여·취소·확정 처리중 | 해당 행동의 처리중 표시와 중복 제출 방지 |
| 입력 오류 | 입력창 아래 구체적인 안내 표시, 저장하지 않음 |
| 요청 실패 | 관련 영역에 실패 안내 표시, 성공 상태로 전환하지 않음 |
| 화면을 연 뒤 정원이 참 | 참여 실패 안내 후 최신 인원·참여 가능 상태 반영 |
| 작업 도중 주문중으로 전환됨 | 서버 결과에 맞춰 변경을 반영하지 않고 잠금 상태와 이유 표시 |
| 현황 조회 실패 | 실패 안내 표시. 실패를 참여자 없음·총액 0원으로 표시하지 않음 |

- `docs/common/db-schema.md`의 `is_meal_open` 기준으로 모집중이면서 `order_time > now()`인 동안만 참여·메뉴 변경·취소·확정이 가능하다. 예약 작업의 상태 전환이 최대 1분 늦어져도 시간에 따른 잠금은 적용된다. 화면에서 겸상 상태가 모집중으로 남아 있다는 이유로 변경을 허용하지 않는다.
- Host가 주문 예정 시간을 수정한 뒤에는 서버에서 다시 조회한 `meals.order_time`을 참여·메뉴 변경·취소·확정의 잠금 기준으로 사용한다. 개인의 `confirmed_at`은 시간 수정으로 해제하지 않는다. 근거: `docs/common/planning.md` §3 주문 예정 시간·주문 확정, `docs/common/db-schema.md` §6 `update_order_time`. 다른 섹션의 변경을 join에 전달하는 연결은 아래 통합 PR 범위를 따른다.
- RLS로 막힌 삭제는 오류 없이 0행 삭제가 될 수 있으므로, 성공 여부는 `api.ts`에서 반영된 행을 확인해 판단한다. 0행 삭제를 참여 취소·메뉴 삭제 성공으로 표시하지 않는다. 근거: `docs/common/db-schema.md` §5 권한.
- 서버 데이터가 참여 가능 여부와 확정 결과의 기준이다. 클라이언트 시계나 버튼 비활성만으로 잠금을 보장하지 않는다.
- join 구현에서는 `JoinSection`이 필요한 데이터를 직접 조회하고, 본인 행동 성공 후 자기 데이터만 재조회한다. 참여·취소 후 본인 참여 상태와 join에서 사용하는 현재 인원, 메뉴 변경·확정 후 내 메뉴·부담액·확정 상태와 Host 취합 현황을 갱신한다.
- 조회한 주문 예정 시간에 도달하면 join의 참여·메뉴 변경·취소·확정을 잠근다. 상태 자동 전환·제외 결과는 최신 서버 데이터를 조회했을 때 반영하며, 주기 조회나 실시간 구독을 추가하지 않는다.
- 다른 섹션 갱신과 공유 데이터의 props 전환은 통합 담당의 별도 통합 PR 범위이며 join 구현의 선행 조건이 아니다. join에서 다른 섹션을 갱신하거나 실시간 구독·주기 조회를 구현하지 않는다.
- 통합 방식은 결정 #75를 따른다. 겸상 정보·내 참여 여부 등 공유 데이터는 `MealDetailPage`에서 조회해 props로 전달하고, 섹션 행동으로 공유 데이터가 변경되면 부모에서 재조회한다. 섹션 전용 데이터는 각 섹션에서 조회한다. 주기 조회는 사용하지 않으며 실시간 구독은 통합 후 필요성을 확인해 별도로 검토한다.
- 잠금과 오류는 색뿐 아니라 문구로 설명한다. 키보드 포커스를 유지하고 주요 터치 영역은 최소 44×44px을 목표로 한다.
