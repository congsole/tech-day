## 1. 무엇을 만들려 했는가 (3줄 이내)

- 사내 직원이 같이 식사하거나 배달을 함께 시킬 사람을 모으고, 메뉴 취합부터 주문·정산까지 한 흐름으로 처리하는 반응형 웹앱
- 메신저로 인원을 모으고 메뉴·금액을 취합하며 생기는 누락과 정산 혼선 감소 목적
- 세 명이 각자 AI 에이전트로 동시에 개발할 때 통하는 협업 방식(문서 주도, 공통 규칙) 실험도 함께 목표

## 2. 역할 분담과 협업 방식 (5줄 이내)

- 공통 역할: 민웅기 기획서·컨텍스트 관리, 유가을 검증·기록·디자인 시스템, 손해솔 통합·DB 스키마
- 기능 분담(세로 슬라이스): 민웅기 로그인·겸상 열기·목록, 유가을 참여·메뉴·주문 확정, 손해솔 주문·정산·공지
- 서로 다른 에이전트(Claude Code, Codex)를 쓰되 AGENTS.md 한 파일의 규칙을 공유해 같은 방식으로 일하게 함
- 문서 주도: 요구사항 문서 PR → 에이전트가 이슈 생성 → 구현 PR. 결정은 decision 이슈(30건), 회고는 retro 이슈(7건)로 기록
- PR은 작게 자주(57건), 다른 사람의 AI가 교차 검토 후 사람이 승인. 통합 담당이 머지하며 충돌 해결

## 3. 부딪힌 이슈와 대응 (3가지 이내 · 각 3줄 이내)

**① AI 검토를 세 번 거쳐도 같은 누락을 못 잡음 (#100, #101)**
- 문제: 실시간 구독 대상에서 메뉴 테이블이 빠졌는데, 세 사람의 AI 검토가 각자 받은 관점(화면·코드 품질·문서 대조)만 보고 모두 통과
- 대응·결과: #101 결정 후 #102에서 메뉴 테이블 구독 추가. 화면×테이블 대조로 사람이 검토 관점을 지정하는 방식은 개선 제안으로 기록

**② 같은 화면을 나눠 구현하며 섹션 간 데이터 불일치 (#61, #75)**
- 문제: 겸상 상세 화면을 기능별 섹션으로 나눠 각자의 에이전트가 구현하면서 같은 데이터를 섹션마다 따로 조회, 참여 직후 공지가 안 보이는 등 불일치 발생
- 대응·결과: 공유 데이터는 상위 페이지에서 한 번 조회해 전달하도록 결정 후 통합 PR에서 일괄 반영, 다른 사용자의 변경은 실시간 구독으로 반영

**③ 병렬 작업의 순서·의존성을 AI가 놓침 (#27, #88)**
- 문제: 에이전트가 PR별 승인 상태만 보고 머지 가능하다고 안내해 통합 충돌 발생. 선행 문서 PR 머지 전에 브랜치를 따 DB 스키마와 기획이 어긋나기도 함
- 대응·결과: 충돌은 통합 담당이 머지하며 해결. 의존 PR 확인 절차는 마무리 기간이라 규칙화하지 못해 미해결로 남음

## 5. 사용한 AI · 툴 · 기술 스택 (자유 기재)

**앱: https://tech-day-nu.vercel.app**

**전체 기록: https://github.com/congsole/tech-day (결정은 `decision`, 회고는 `retro` 라벨 이슈)**

**배운 것: 검토 횟수만으로는 누락을 막지 못함. 범위·관점·의존성은 명시적으로 확인해야 함**
- 세 사례 모두 에이전트가 받은 관점, 자기 섹션, 개별 PR 상태 위주로 판단하며 다른 화면의 구독 대상, 섹션 간 공유 데이터, PR에 적힌 선행 머지 조건을 놓침
- 범위는 문서로 고정하고, 검토를 요청할 때 확인할 관점과 의존성을 함께 명시하는 것을 개선 방향으로 정리

**AI 도구: 도구는 각자, 규칙은 하나**
- 손해솔·민웅기 Claude Code, 유가을 Codex. 도구를 통일하지 않고 각자 익숙한 에이전트를 쓰되, 같은 규칙과 문서를 따르게 하는 데 집중

**규칙 파일 하나로 서로 다른 에이전트를 같은 방식으로 움직임**
- 왜: 도구마다 규칙 파일이 따로 있으면 내용이 갈라지고, 사람용·에이전트용 문서가 겹치면 동기화 누락 발생(초기 회고 #1)
- 어떻게: 규칙은 AGENTS.md 한 파일에만 작성, 도구별 설정 파일은 이 파일을 불러오기만 함. Claude Code·Codex·Gemini CLI·Antigravity CLI 공용
- 확인: 에이전트에게 규칙 확인을 요청하면 정해진 응답(TECHDAY-OK)이 나오는지로 규칙 로딩 여부 점검

**문서가 원천: 에이전트가 임의로 채울 빈칸을 없앰**
- 왜: 에이전트는 세션마다 기억이 없어 문서에 없는 부분을 임의로 채움. 세 사람의 에이전트가 각자 채우면 결과가 서로 어긋남
- 어떻게: 공통 문서(기획서·도메인 용어집·DB 스키마·디자인 시스템)와 기능별 요구사항 정의서 작성. 요구사항마다 ID와 Given/When/Then 인수 조건 부여, 미정 부분은 [확인 필요]로 표시해 에이전트가 구현하지 않고 멈추게 함
- 흐름: 문서 PR 승인 → 에이전트가 요구사항별 이슈 생성(본문엔 문서 경로·ID만) → 구현 요청 → 에이전트가 문서를 읽고 인수 조건대로 구현 → PR. 요구사항 21개를 이 흐름으로 구현
- 스택 선택에도 반영: 에이전트 작성 정확도가 높은 React + TypeScript, 에이전트마다 기본 UI를 따로 만들지 않도록 컴포넌트 라이브러리(Mantine) 채택

**사람과 AI의 역할 경계: 에이전트는 초안, 사람은 결정**
- 에이전트: 이슈·결정 기록 초안 작성, 요구사항 이슈 생성, 구현, PR 검토 의견
- 사람: 초안 승인 후 이슈 생성, 승인·머지·통합. 에이전트가 확인 없이 이슈를 만든 일을 계기로 규칙화(#9)
- 개인별 교정 사항은 에이전트 메모리에 누적(이슈는 승인 후 생성, 리뷰는 결론 먼저, 외부 발송 전 수신 주소 확인 등)

**AI 교차 검토: 리뷰어가 결함을 재현해 확인**
- 작성자가 아닌 사람의 에이전트가 PR 검토, 문서와 코드가 맞는지 대조
- 검토 단계에서 발견한 결함: 시각 비교 오류로 마감 후에도 버튼이 남는 문제, 소켓 재연결 중 변경 누락, 늦게 도착한 응답이 최신 상태를 덮는 문제 등
- 검증 방식: 응답 순서처럼 재현이 어려운 문제는 모의 테스트로 순서를 제어해 확인하고, 재연결 중 변경 누락 등은 실제 Supabase에서도 재현·수정 확인
- 검토를 여러 번 받아도 관점이 겹치면 같은 누락을 놓친다는 회고(#100)에서, 검토 관점을 사람이 지정하자는 개선 제안 도출

**협업 기록과 구조: 결정·회고를 GitHub 이슈에 남기고 충돌을 구조로 줄임**
- decision 이슈 30건
  - 왜: 규칙 파일(AGENTS.md)에 결정의 근거까지 적으면 규칙이 비대해져 비효율적이고, 적지 않으면 근거를 남길 곳이 없음
  - 어떻게: 리포지토리와 연동되어 사람은 쉽게 찾아보고 에이전트는 컨텍스트로 읽을 수 있는 GitHub 이슈를 기록 공간으로 선택. 규칙 파일엔 결정만, 이슈엔 결정·이유 기록
- retro 이슈 7건: AI 협업과 검증·기록 과정에서 발견한 문제를 회고로 기록
- 충돌 줄이는 구조: dev 기본 브랜치, 문서(docs/)·구현(feature/) 브랜치 분리, 기능별 폴더·라우트 파일, 겸상 상세 화면은 기능별 섹션으로 분리
- 검토 체계: 같은 기능의 문서·코드 PR은 같은 사람이 승인하는 순환 리뷰, 공통 문서·규칙 변경은 전원 승인. 마무리 기간에는 2인 상호 검토로 전환
- 규모: 9/30 ~ 11/2, PR 57건, 이슈 63건(decision 30건, retro 7건 포함, 2026-11-03 GitHub 조회 기준, 열림·닫힘 포함). GitHub 작업은 4개 도구 공통으로 gh CLI 사용
