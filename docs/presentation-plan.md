### 중심 메시지

**이 프로젝트에서는 검토를 여러 번 받아도 연결된 부분의 누락을 놓쳤다. 무엇을 함께 확인할지, 어떤 순서로 합칠지를 구체적으로 정하는 일이 남았다.**

AI의 일반적인 능력에 관한 결론이 아니라, 이 팀의 개발 기록에서 관찰한 내용으로 말한다. 공통 문서와 교차 검토가 실제로 어떻게 쓰였는지 보여주고, 그것만으로 해결되지 않았던 문제도 함께 남긴다.

### 청중과 말투

- PR·코드 리뷰 경험이 있는 사내 개발자를 주요 청중으로 가정한다. Supabase나 앱 내부 구조에 대한 사전 지식은 요구하지 않는다.
- 발표자는 한 명, 팀의 경험을 소개할 때는 우리 팀이라는 표현을 쓴다. 개인별 감정이나 당시 대화는 추정하지 않는다.
- 위트는 검토 세 번과 누락 한 개, 같은 화면의 서로 다른 참여 상태, 승인과 머지 순서의 어긋남에서 만든다. 가상의 AI 답변, 팀원 탓, 도구별 우열 비교는 넣지 않는다.
- 사건을 소개할 때는 증상 → 협업 구조와 원인 → 실제 대응 → 남은 점 순서로 말한다. 사례의 제시 순서는 설명을 위한 배열이며 실제 발생 순서를 뜻하지 않는다.

### 비중을 낮추거나 본편에서 제외할 내용

- 기능별 시연, 인증 절차, 전체 기술 스택 설명: 앱 소개 한 장으로 제한한다.
- PR·이슈 총량과 도구별 기능 비교: 발표의 중심 메시지를 설명하는 데 필요하지 않으므로 본편에 넣지 않는다. 집계 정보는 현재 요약본의 2026-11-03 기준을 따른다.
- 개발 시간 단축률, 비용 절감, 사용자 반응, 정산 혼선 감소 성과: 측정 근거가 없으므로 주장하지 않는다. 정산 혼선 감소는 개발 목적이다.
- 상세 DB 구조, 코드 조각, 모든 버그 목록: 협업 문제를 설명하는 데 필요한 구독 대상·공유 데이터·선행 조건만 다룬다.

## 4. 슬라이드별 구성안

### 1. 검토 세 번, 누락 하나

**핵심 메시지**

같은 누락이 세 차례의 AI 검토를 지나갔다. 이 사건을 따라가며 팀의 협업 방식을 살펴본다.

**실제 표시할 내용**

> 검토 세 번, 누락 하나
>
> AI를 활용한 앱 개발 협업기 — 겸상
>
> 다른 참여자의 메뉴 변경이 취합 현황에 반영되지 않았다

**발표자가 설명할 내용**

- “세 사람이 각자 AI와 앱을 만들었습니다. AI 검토도 세 번 있었는데, 다른 사람이 바꾼 메뉴가 화면에 반영되지 않는 누락은 남았습니다.”
- 세 번은 동일한 체크리스트로 반복한 검토가 아니라 서로 다른 관점의 검토였다. 자세한 경위는 8장에서 설명한다.
- “오늘은 이 앱을 만들면서 서로 무엇을 맞췄고, 어디서 어긋났는지 이야기하겠습니다.”

**예상 발표 시간**: 35초. 제목을 읽고 2초 쉬는 시간 포함.

**화면 구성 및 전환**

- 넓은 여백에 제목 한 줄. 먼저 ‘검토 세 번’을 보여주고 클릭 한 번으로 ‘누락 하나’를 강조한다.
- 증상 한 줄은 그다음에 나타낸다. 성공 체크 표시 세 개로 표현하지 않는다. 세 검토가 전체 앱의 통과를 보증한 것처럼 보일 수 있기 때문이다.
- 다음 장에서 같은 ‘겸상’ 글자가 제품 소개의 제목 위치로 이어지도록 전환한다.

**다음 장 연결 멘트**: “먼저, 메뉴가 바뀌어야 했던 이 앱부터 짧게 보여드리겠습니다.”

**근거**: 수정 요약본 §3 ①, [회고 #100](https://github.com/congsole/tech-day/issues/100).

### 2. 겸상: 같이 먹는 앱을 같이 만들기

**핵심 메시지**

제품은 하나의 식사 흐름을 완성하는 범위였고, 프로젝트에는 각자의 AI와 함께 개발하는 협업 실험도 포함됐다.

**실제 표시할 내용**

> 겸상
>
> 같이 먹고, 같이 시키고, 깔끔하게 나누는 사내 식사 모집 웹앱
>
> 겸상 열기 → 참여 → 메뉴 취합 → 주문 → 정산
>
> 핵심 요구사항 21개 구현 · 정산은 금액 표시까지

**발표자가 설명할 내용**

- 메신저로 인원을 모으고 메뉴·금액을 취합하면서 생기는 누락과 정산 혼선을 줄이려는 목적이었다.
- 실제 주문과 송금은 앱 밖에서 한다. 앱의 정산은 각자가 부담할 금액을 보여주는 범위다.
- 세 사람이 각자 에이전트를 사용해 동시에 개발할 때 무엇을 맞춰야 하는지도 프로젝트의 목표였다.
- 요구사항 21개 구현은 수정 요약본의 완료 범위다. 사용자 반응이나 업무 개선 효과를 측정했다는 뜻은 아니다.

**예상 발표 시간**: 40초.

**화면 구성 및 전환**

- 중앙에 다섯 단계의 가로 흐름을 배치한다. 발표 중 ‘참여’와 ‘메뉴 취합’을 차례로 강조해 뒤의 사례를 위한 위치만 익히게 한다.
- 텍스트만으로 완결되게 만든다. 실제 화면 캡처가 없어도 설명이 가능하며, 라이브 데모나 영상으로 전환하지 않는다.
- 다섯 단계를 다음 장의 기능 담당 범위와 연결한다.

**다음 장 연결 멘트**: “이 흐름을 세 사람이 나눠 맡았고, 쓰는 AI도 같지는 않았습니다.”

**근거**: 수정 요약본 §1·§4, `docs/common/planning.md` §2.

### 3. 도구는 각자, 규칙은 하나

**핵심 메시지**

서로 다른 도구가 같은 규칙을 읽게 하려 공통 규칙을 한 파일로 모았다.

**실제 표시할 내용**

> 민웅기·손해솔: Claude Code / 유가을: Codex
>
> 공통 규칙: `AGENTS.md`
>
> 규칙 확인 → `TECHDAY-OK`

**발표자가 설명할 내용**

- 도구별 규칙 파일이 갈라지면 같은 작업에도 서로 다른 지시를 따를 수 있어, 공통 규칙은 `AGENTS.md`에만 두고 도구별 설정은 이를 읽게 했다.
- “도구는 달랐지만 규칙을 읽었는지 확인할 때의 대답은 같았습니다. TECHDAY-OK.”
- 확인 응답은 규칙 로딩을 점검하는 약속이다. 이후 행동의 규칙 준수를 보증하지 않는다. 네 도구용 규칙 지원과 실제 사용한 두 도구도 구분한다.

**예상 발표 시간**: 45초.

**화면 구성 및 전환**

- 도구 이름 두 묶음이 같은 규칙 파일을 가리키는 간단한 도식.
- 확인 문구를 한 번 노출하고 ‘규칙 로딩 확인 예시’로 표시한다.

**다음 장 연결 멘트**: “같은 규칙에 더해, 세션이 달라도 다시 읽을 요구사항이 필요했습니다.”

**근거**: 수정 요약본 §5의 AI 도구·규칙 파일, 회고 #1.

### 4. 구현 전에 합의부터

**핵심 메시지**

세션을 넘어 같은 맥락을 전달하기 위해, 만들 동작과 구현의 경계를 문서에 남겼다.

**실제 표시할 내용**

> 문서 PR 승인·머지 → 요구사항 이슈 → 구현 PR
>
> 요구사항 ID + Given / When / Then
>
> `[확인 필요]`가 남으면 구현 중단

**발표자가 설명할 내용**

- #7에서는 세션마다 맥락을 다시 전달해야 한다는 문제의식으로 문서를 팀의 공통 기준으로 정했다. 에이전트의 기억 기능에 관한 일반론보다 이 팀이 선택한 전달 방법을 설명한다.
- 요구사항 ID와 인수 조건으로 만들 동작을 정하고, 이슈에는 문서 경로와 ID를 넣어 본문이 갈라지지 않게 했다.
- 미정 부분은 에이전트가 채우게 두지 않고 `[확인 필요]`로 표시했다.

**예상 발표 시간**: 45초.

**화면 구성 및 전환**

- 작업 흐름 한 줄과 인수 조건을 차례로 보여준다.
- `[확인 필요]`를 표시하면 흐름 강조를 멈춘다.

**다음 장 연결 멘트**: “같은 요구사항을 보면서도 서로 기다리지 않고 개발하려고, 기능을 나눴습니다.”

**근거**: 수정 요약본 §5의 문서가 원천, [문서 주도 결정 #7](https://github.com/congsole/tech-day/issues/7).

### 5. 기능은 나누고, 자주 합치기

**핵심 메시지**

서로 기다리지 않고 개발하도록 기능을 나누고, 파일 충돌을 줄이면서 통합 문제는 일찍 발견하려 했다.

**실제 표시할 내용**

| 사람 | 기능 담당 | 공통 역할 |
|---|---|---|
| 민웅기 | 로그인·겸상 열기·목록 | 기획·컨텍스트 |
| 유가을 | 참여·메뉴·주문 확정 | 검증·기록·디자인 |
| 손해솔 | 주문·정산·공지 | 통합·DB 스키마 |

> 기능별 개발 → 상세 화면의 섹션 분리 → 작은 PR로 자주 통합

**발표자가 설명할 내용**

- #29에서 기능을 API부터 화면까지 세로로 나누어 서로 기다리지 않고 개발하도록 정했다. 표의 이름과 기능을 모두 읽기보다 분담 원칙을 설명한다.
- 함께 쓰는 겸상 상세는 같은 파일을 동시에 수정하는 충돌을 피하려 기능별 섹션으로 나눴다(#39).
- 작은 PR을 자주 올리고 통합 담당이 합치면서 충돌을 일찍 발견하려 했다(#29). 파일 분리만으로 데이터 갱신이나 PR 의존성까지 해결한 것은 아니다.

**예상 발표 시간**: 45초.

**화면 구성 및 전환**

- 역할 표를 먼저 보여주고 아래에 상세 화면의 기능별 섹션을 간결하게 표시한다.
- 파일 분리와 작은 PR의 선택 이유를 짧은 보조 문구로 붙인다.

**다음 장 연결 멘트**: “각자 만든 것을 누가 확인하고 승인할지도 정했습니다.”

**근거**: 수정 요약본 §2, `docs/common/planning.md` §4, [역할 분담 #29](https://github.com/congsole/tech-day/issues/29), [섹션 분리 #39](https://github.com/congsole/tech-day/issues/39).

### 6. 검토 담당과 승인 지점 정하기

**핵심 메시지**

문서를 아는 사람이 구현을 이어서 검토하고, 에이전트가 만든 초안은 사람이 확인하도록 정했다.

**실제 표시할 내용**

> 같은 기능: 문서 PR 승인자 → 코드 PR 검토
>
> 에이전트: 초안·구현·검토 의견 / 사람: 승인·통합
>
> 정한 것: 검토 담당 / 남은 것: 누락을 찾는 공통 검토 관점

**발표자가 설명할 내용**

- 문서 내용을 아는 사람이 코드를 정확하고 빠르게 검토하도록, 같은 기능의 문서·코드 PR 승인자를 같게 하는 순환 검토를 선택했다(#5). 마무리 기간에는 가을·해솔의 상호 검토로 전환했다.
- 에이전트가 확인 없이 이슈를 만든 일을 계기로, 초안을 보여주고 사람의 승인을 받은 뒤 생성하도록 정했다(#9).
- 승인자는 정했지만 화면의 표시 데이터와 구독 대상을 대조하는 공통 검토 관점까지 정하지는 않았다(#100). 뒤의 사건에서 드러난 빈틈이다.

**예상 발표 시간**: 45초.

**화면 구성 및 전환**

- 문서 PR에서 코드 PR로 이어지는 같은 검토자 표시와 사람의 승인 지점을 보여준다.
- 아래에 검토 담당과 검토 관점을 구분한다.

**다음 장 연결 멘트**: “이렇게 나눈 구조가 실제 화면에서 만났을 때, 첫 번째 어긋남이 생겼습니다.”

### 7. 같은 화면인데, 참여 여부가 다르다

**핵심 메시지**

기능을 나눠 구현해도 여러 섹션이 쓰는 데이터의 갱신은 함께 설계해야 했다.

**실제 표시할 내용**

> 참여 완료
>
> 그런데 공지 띠는 나타나지 않았다
>
> 섹션마다 따로 조회한 참여 여부
> → 공유 데이터는 상위 페이지에서 조회·전달

**발표자가 설명할 내용**

- 20초: 같은 파일의 동시 수정 충돌을 피하려 겸상 상세를 기능별 섹션으로 나눴다(#39). 그 구조에서 여러 섹션이 참여 여부 같은 데이터를 각각 조회했다. 참여 직후 공지 띠가 나타나지 않는 불일치가 생겼다.
- 20초: 참여 섹션에서 행동이 성공해도, 공지 섹션이 별도로 읽은 참여 여부까지 함께 갱신되는 구조는 아니었다. 각 기능의 성공과 화면 전체 상태의 일치가 연결되지 않았다.
- 20초: #75에서 여러 섹션이 공유하는 데이터는 상위 페이지에서 조회·전달하고, 이를 바꾸는 행동 뒤에는 부모에서 다시 조회하도록 결정했다. 통합 담당이 통합 PR에서 반영했다. 섹션 전용 데이터는 해당 섹션이 계속 맡았다.
- 10초: 다른 사용자의 변경을 받는 실시간 구독은 이후 별도로 반영했다. #75에서 실시간 구독까지 함께 확정한 것으로 설명하지 않는다.

**예상 발표 시간**: 70초.

**화면 구성 및 전환**

- 실제 앱 화면을 복제하지 않는 설명용 도식. 왼쪽에 ‘참여’, 오른쪽에 ‘공지’를 놓고, 각자가 읽는 ‘참여 여부’를 각각 표시한다.
- 클릭하면 공통 ‘참여 여부’ 하나가 위쪽에 자리 잡고 양쪽에 전달되는 모습으로 전환한다. ‘개선 전 / 반영한 구조’를 명시한다.
- 별도 조작 없이 두 상태를 비교할 수 있도록 전환 후 핵심 문구를 유지한다. CSS 애니메이션을 쓰더라도 한 번만 재생한다.

**다음 장 연결 멘트**: “공유 데이터를 맞춘 뒤에도, 다른 사람이 바꾼 메뉴까지 들어오게 하려면 확인할 연결이 더 있었습니다.”

### 8. 세 번의 검토가 비워 둔 한 칸

**핵심 메시지**

검토 담당을 정하고 결함도 재현했지만, 화면의 데이터와 구독 대상을 전체 대조하는 관점은 빠져 있었다.

**실제 표시할 내용**

> 정한 것: 문서를 아는 검토자 / 빠진 확인: 표시 데이터 × 구독 대상
>
> 실제 수정: 메뉴 테이블 구독 추가
> 개선 제안: 화면 × 테이블 대조

| 교차 검토에서 찾은 문제 | 확인 방식 |
|---|---|
| 늦은 응답이 최신 상태를 덮음 | 모의 테스트로 응답 순서 제어 |
| 재연결 중 변경 누락 | 실제 Supabase에서도 재현·수정 확인 |

**발표자가 설명할 내용**

- 15초: 도입의 사건으로 돌아온다. #5로 같은 기능의 문서·코드 검토자는 정했지만, 실시간 구독을 정한 문서 자체에서 메뉴 테이블이 빠졌다. 작성 쪽 에이전트도 문서의 테이블을 기준으로 구현했다.
- 20초: 담당 화면, 응답 순서 등 구현 품질, 문서와 구현 일치의 세 관점으로 검토했으나, 화면에 필요한 데이터 전체가 구독 대상에 있는지는 대조하지 않았다(#100). 문서와 코드의 일치만으로 문서의 누락까지 잡지는 못했다.
- 20초: Host 취합 현황에서 다른 참여자의 메뉴 변경이 반영되지 않는 현상을 확인했고, #101 결정 후 #102에서 메뉴 구독을 추가했다. 화면 × 테이블 대조는 개선 제안이며 효과를 검증한 결과는 없다.
- 25초: 같은 교차 검토에서 응답 순서와 재연결 결함은 찾아 재현했다. 응답 순서는 모의 테스트로 제어했고, 재연결은 실제 Supabase에서도 확인했다. 맡긴 범위에서는 항상 정확하다는 결론 대신 실제 확인한 두 사례로 효용을 설명한다.
- 10초: “구체적인 결함을 재현한 검토에서도, 무엇을 빠뜨렸는지 확인하는 관점은 별도로 필요했습니다.”

**예상 발표 시간**: 90초.

**화면 구성 및 전환**

- 먼저 세 검토 관점과 비어 있던 대조 항목을 보여준다. 실제 전수 대조표가 있었던 것처럼 제시하지 않는다.
- 실제 수정과 개선 제안을 구분한 뒤, 같은 장에서 결함 재현 두 행을 순차 노출한다. 설명이 끝난 문구는 축약해 한 화면의 밀도를 낮춘다.
- 모의·실환경 표시는 유지하고 코드·로그 화면은 추가하지 않는다.

**다음 장 연결 멘트**: “데이터 연결에서 빠진 확인이 있었다면, PR을 합치는 순서에서도 빠진 확인이 있었습니다.”

**근거**: 수정 요약본 §3 ①·§5, [순환 리뷰 #5](https://github.com/congsole/tech-day/issues/5), [회고 #100](https://github.com/congsole/tech-day/issues/100), [구독 추가 PR #102](https://github.com/congsole/tech-day/pull/102), #116 검토 반영 사항 1번.

### 9. 승인됐다고 먼저 머지하면

**핵심 메시지**

개별 PR의 승인 상태와 여러 PR을 합쳐야 하는 순서는 별개였다. 이미 적혀 있던 선행 조건도 놓쳤다.

**실제 표시할 내용**

> 승인 확인 ≠ 머지 순서 확인
>
> #88: 명시된 선행 머지 조건 누락 → 통합 충돌
> #27: 선행 문서 머지 전 분기 → 스키마와 기획 불일치
>
> 충돌 해결: 통합 담당
> 의존 PR 확인 절차: 규칙화하지 못한 과제

**발표자가 설명할 내용**

- 20초: 병렬 개발과 작은 PR의 잦은 통합을 선택했지만(#29), 연관 PR 의존성을 확인하는 공통 절차는 정하지 않았다. #88에서는 #80에 선행 머지와 통합 절차가 적혀 있었다. 에이전트는 #71·#72 각각의 승인 상태와 머지 가능 여부를 보고 안내했고, 이들이 먼저 머지된 뒤 #80에서 충돌이 발생했다. 요구된 순서는 #80이 먼저였다.
- 15초: 별개의 앞선 사례인 #27에서는 공통 문서 변경이 반영되기 전에 DB 스키마 브랜치를 따서, 주문중 상태 변경이 빠진 채 기획과 스키마가 어긋났다. 두 사건이 같은 날 연속으로 발생했다고 말하지 않는다.
- 15초: 통합 담당이 충돌을 해결했다. 연관 PR 의존성 확인과 선행 조건 교차 링크는 개선 방향으로 남았으며 마무리 기간에 규칙화하지 못했다.
- 10초: “이 경우는 AI가 전달받지 못한 정보를 추측해야 했던 문제가 아닙니다. 적혀 있던 순서도 확인에서 빠졌습니다.”

**예상 발표 시간**: 60초.

**화면 구성 및 전환**

- 첫 화면에 ‘승인’과 ‘순서’를 큰 글자로 나란히 둔다.
- #88을 설명할 때 ‘지정된 순서: #80 → #71·#72’와 ‘실제 선행 머지: #71·#72’를 두 줄로 보여준다. 둘의 차이를 수동 클릭으로 강조한다.
- #27은 아래의 짧은 별도 사례로만 추가한다. 복잡한 Git 그래프나 충돌 코드 화면은 쓰지 않는다.
- 마지막에는 해결된 충돌과 남은 절차를 함께 보이게 한다.

**다음 장 연결 멘트**: “세 사건을 놓고 보니, 정한 구조와 그 안에서 빠진 확인을 함께 기록할 필요가 있었습니다.”

**근거**: 수정 요약본 §3 ③, 역할 분담 #29, [머지 순서 회고 #88](https://github.com/congsole/tech-day/issues/88), [문서 변경 시점 회고 #27](https://github.com/congsole/tech-day/issues/27).

### 10. 정한 것과 남은 확인을 함께 기록하기

**핵심 메시지**

선택한 협업 구조, 그때 정하지 않은 부분, 실제 대응과 제안을 함께 정리한다.

**실제 표시할 내용**

> decision: 결정과 이유 / retro: 관찰과 개선 제안

| 정한 구조 | 당시 정하지 않은 부분 | 대응·현재 상태 |
|---|---|---|
| 기능별 섹션 분리 | 섹션 간 공유 데이터 갱신 | 상위 조회·전달 반영(#75) |
| 문서·코드의 같은 검토자 | 표시 데이터 × 구독 대상 대조 | 메뉴 구독 추가 완료 / 대조 방식은 제안 |
| 병렬 개발·작은 PR 통합 | 연관 PR 의존성 확인 절차 | 충돌 해결 / 절차는 제안 |

> 다음 요청 예시: 표시 데이터와 구독 대상, 관련 PR의 선행 머지 조건을 대조해 주세요.
> 제안 · 효과 미확인

**발표자가 설명할 내용**

- 20초: 규칙 파일이 비대해지지 않도록 결정과 이유는 decision에, 관찰과 개선 제안은 retro에 남겼다. 표는 발표를 위해 기록을 다시 정리한 것이며 당시 사용한 추적표가 아니다.
- 30초: 섹션 분리는 유지하면서 공유 데이터 조회를 통합했고, 검토에서 빠진 메뉴 구독은 추가했다. 의존성 사례는 선행 조건이 개별 PR에 적혀 있었어도 확인 절차에서 놓친 문제다. 조건 자체가 없었다고 설명하지 않는다.
- 15초: 하단 요청은 #100·#88의 제안을 풀어 쓴 예시다. 두 회고는 공통 규칙으로 추가하지 않고 관찰 기록으로 종료했으며, 이 요청 방식의 효과도 아직 검증하지 않았다. 머지 차단 사항과 후속 통합 작업을 구분해 달라는 요청도 필요에 따라 덧붙일 수 있다.

**예상 발표 시간**: 65초.

**화면 구성 및 전환**

- 세 행을 앞선 사건 순서대로 보여주고 정한 구조·빈틈·대응을 가로로 연결한다.
- 적용 완료와 제안은 글자로 구분한다. 표 아래 요청 예시는 마지막 클릭에 노출하며 실제 대화창으로 꾸미지 않는다.

**다음 장 연결 멘트**: “앱의 핵심 흐름은 구현했고, 협업 방식에는 이렇게 함께 확인할 일이 남았습니다.”

## 5. Reveal.js 구현 단계에 전달할 연출 원칙

- 화면 비율은 16:9를 가정한다. 한글 산세리프와 충분한 여백을 기본으로 하고, 파일명·확인 문구에만 고정폭 글꼴을 고려한다.
- 흐름은 수평 이동 한 줄로 구성한다. 10분 본편에 수직 하위 슬라이드나 분기 탐색을 넣지 않는다.
- 순차 노출은 발표자의 클릭으로 진행한다. 자동 재생·자동 넘김·반복 애니메이션은 사용하지 않는다.
- 위치가 이어지는 전환은 1→2장, 3→4장처럼 의미상 이어지는 곳에 한정한다. 나머지는 짧은 페이드나 즉시 전환으로 충분하다.
- CSS 애니메이션은 공유 데이터가 한 곳으로 모이는 변화, 확인 항목의 강조처럼 설명을 돕는 곳에만 사용한다. 효과를 제거해도 사실과 관계가 읽혀야 한다.
- 화면은 한 장에 한 메시지를 유지한다. 역할·검증 방식·적용 상태는 비교표를 쓰되, 모든 장을 같은 카드 배열로 만들지 않는다.
- 증거는 간결한 출처 번호와 발표자 노트의 링크로 연결한다. 실제 이슈를 새로 그린 대화창이나 가짜 로그로 재현하지 않는다.
- 화면 캡처를 추가한다면 실제 앱·이슈에서 확보한 이미지만 사용한다. 현재 구성은 캡처 없이 텍스트·도식·표만으로 완결된다.
- 영상, 영상 자리 표시자, 재생 버튼, 라이브 데모는 구성에 포함하지 않는다.
- 이번 문서는 연출 아이디어만 제안한다. HTML·CSS·JavaScript 코드나 Reveal.js 설정은 작성하지 않는다.

## 6. 시간과 흐름 검토

### 시간 합계

- 도입·앱 소개(1–2장): 75초, 1분 15초.
- 협업 구조와 선택 이유(3–6장): 180초, 3분.
- 시행착오 세 사례와 검토 효용(7–9장): 220초, 3분 40초.
- 기록·다음 요청·종료(10–11장): 95초, 1분 35초.
- 본편 합계: 570초, 9분 30초. 현장 여유 30초를 더해 10분으로 계획한다.
- 각 장의 시간은 발화·클릭·정지를 포함한 편성 목표다. 설명 항목은 완성 대본이 아니며 실제 시간은 리허설에서 확인한다.

### 흐름 검토

- 1장의 사건은 8장에서 원인·대응을 설명한다. 2장은 제품 맥락만 짧게 제공한다.
- 3–6장은 규칙·문서·기능 분담·검토를 무엇 때문에 선택했는지 설명한다. 뒤의 사건을 모두 예방했다는 근거로 사용하지 않는다.
- 5장의 섹션 분리는 7장의 공유 상태 문제로, 6장의 검토 담당 지정은 8장의 관점 누락으로 연결한다.
- 5장의 병렬 개발·잦은 통합은 9장의 분기·머지 순서 문제와 연결한다. 명시된 선행 조건과 이를 확인하는 공통 절차를 구분한다.
- 7–9장의 세 사건은 공유 상태·검토 관점·작업 순서라는 다른 문제다. 하나의 AI 능력 문제로 뭉뚱그리지 않는다.
- 8장에서 누락과 결함 재현을 함께 설명하되, 구체적인 성공 사례를 맡긴 범위에서 항상 정확하다는 결론으로 확대하지 않는다.
- 10장은 앞선 구조·빈틈·대응을 같은 행으로 정리하고 요청 예시를 짧게 덧붙인다. 11장은 질문 하나로 마친다.

### 리허설에서 시간을 넘길 경우

1. 3장의 규칙 로딩 예시 발화를 줄여 약 5초 축소.
2. 5장의 역할 표를 행별로 읽지 않고 분담·충돌 방지 원칙 중심으로 설명해 약 10초 축소.
3. 9장의 #27을 한 문장으로 줄여 약 10초 축소. #88의 명시된 선행 조건 누락은 유지.
4. 10장의 요청 예시를 한 문장만 읽어 약 5초 축소. 적용 완료와 제안 구분은 유지.
5. 8장의 모의·실환경 검증 구분과 실제 수정·개선 제안 구분은 축소 시에도 유지.

- 협업 구조의 선택 이유가 뒤의 세 사례를 이해하는 데 충분한지.
- 8장의 누락·재현 성과 통합과 10장의 정리 표가 발표 시간 안에 읽히는지.
