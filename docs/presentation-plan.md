### 중심 메시지

**이 프로젝트에서는 검토를 여러 번 받아도 연결된 부분의 누락을 놓쳤다. 무엇을 함께 확인할지, 어떤 순서로 합칠지를 구체적으로 정하는 일이 남았다.**

기획 합의와 결정 전달부터 실제 구현·검증까지, 팀이 기준을 맞춰 가는 과정을 보여준다. AI의 일반적인 능력에 관한 결론이 아니라, 이 팀의 개발 기록에서 관찰한 내용으로 말한다. 공통 문서와 교차 검토가 실제로 어떻게 쓰였는지 보여주고, 그것만으로 해결되지 않았던 문제도 함께 남긴다. 문서가 시간 차이를 메워준 효용과 승인·기록의 부담을 함께 다루며, 다음에 절차의 무게를 어떻게 조절할지 질문한다.

### 청중과 말투

- PR·코드 리뷰 경험이 있는 사내 개발자를 주요 청중으로 가정한다. Supabase나 앱 내부 구조에 대한 사전 지식은 요구하지 않는다.
- 발표자는 한 명, 팀의 경험을 소개할 때는 우리 팀이라는 표현을 쓴다. 발표자는 가을로 가정하며, 다른 사람이 발표하면 가을의 개인 경험을 1인칭으로 읽지 않는다. 개인별 감정이나 당시 대화는 추정하지 않는다.
- 위트는 초기 아이디어와 간단하게 정한 주제의 차이, 사다리 배정 뒤 역할 조정, 호칭 변화, 엇갈린 참여 시간, 검토 세 번과 누락 한 개, 같은 화면의 서로 다른 참여 상태, 승인과 머지 순서의 어긋남에서 만든다. 가상의 AI 답변, 팀원 탓, 도구별 우열 비교는 넣지 않는다.
- 사건을 소개할 때는 증상 → 협업 구조와 원인 → 실제 대응 → 남은 점 순서로 말한다. 사례의 제시 순서는 설명을 위한 배열이며 실제 발생 순서를 뜻하지 않는다.

### 비중을 낮추거나 본편에서 제외할 내용

- 채팅과 개인 회고는 필요한 부분만 인용한다. 새로 만든 웃음 포인트는 실제 대화 인용과 구분한다.

## 4. 슬라이드별 구성안

### 1. 검토 세 번, 누락 하나

**핵심 메시지**

같은 누락이 세 차례의 AI 검토를 지나갔다. 이 사건을 따라가며 팀의 협업 방식을 살펴본다.

**실제 표시할 내용**

> 검토 세 번, 누락 하나
>
> AI를 활용한 앱 개발 협업기 — 겸상
>
> 다른 참여자의 메뉴 변경이 취합 현황에 반영되지 않았다

**발표자가 설명할 내용**

- “세 사람이 각자 AI와 앱을 만들었습니다. AI 검토도 세 번 있었는데, 다른 사람이 바꾼 메뉴가 화면에 반영되지 않는 누락은 남았습니다.”
- 세 번은 동일한 체크리스트로 반복한 검토가 아니라 서로 다른 관점의 검토였다. 자세한 경위는 15장에서 설명한다.
- “오늘은 이 앱을 만들면서 서로 무엇을 맞췄고, 어디서 어긋났는지 이야기하겠습니다.”

**예상 발표 시간**: 35초. 제목을 읽고 2초 쉬는 시간 포함.

**화면 구성 및 전환**

- 넓은 여백에 제목 한 줄. 먼저 ‘검토 세 번’을 보여주고 클릭 한 번으로 ‘누락 하나’를 강조한다.
- 증상 한 줄은 그다음에 나타낸다. 성공 체크 표시 세 개로 표현하지 않는다. 세 검토가 전체 앱의 통과를 보증한 것처럼 보일 수 있기 때문이다.
- 다음 장에서 같은 ‘겸상’ 글자가 제품 소개의 제목 위치로 이어지도록 전환한다.

**다음 장 연결 멘트**: “그 이야기에 앞서, 무엇을 만들지 고민하던 때로 잠깐 돌아가 보겠습니다.”

### 2. 주제 하나만 가져오기로 했습니다

**핵심 메시지**

처음에는 다들 규모가 있는 아이디어를 생각했지만, 함께 진행할 주제는 간단한 겸상으로 정했다.

**실제 표시할 내용**

> 처음 떠올렸던 것들
>
> 사내 서버 모니터링 · 업무 관리 통합 툴 · 개발 자동화의 협업 확장
>
> 최종 선택: 같이 먹을 사람을 모으는 앱, 겸상

**발표자가 설명할 내용**

- 주제를 하나씩 생각해 오기로 했고, 처음에는 다들 볼륨이 있는 아이디어를 떠올렸다. 결국 함께 진행할 주제는 간단하게 정했다는 흐름으로 소개한다.

### 3. 겸상: 같이 먹는 앱을 같이 만들기

**핵심 메시지**

제품은 하나의 식사 흐름을 완성하는 범위였고, 프로젝트에는 각자의 AI와 함께 개발하는 협업 실험도 포함됐다.

**실제 표시할 내용**

> 겸상
>
> 같이 먹고, 같이 시키고, 깔끔하게 나누는 사내 식사 모집 웹앱
>
> 겸상 열기 → 참여 → 메뉴 취합 → 주문 → 정산
>
> 핵심 요구사항 21개 구현 · 정산은 금액 표시까지

**발표자가 설명할 내용**

- 메신저로 인원을 모으고 메뉴·금액을 취합하면서 생기는 누락과 정산 혼선을 줄이려는 목적이었다.
- 실제 주문과 송금은 앱 밖에서 한다. 앱의 정산은 각자가 부담할 금액을 보여주는 범위다.
- 세 사람이 각자 에이전트를 사용해 동시에 개발할 때 무엇을 맞춰야 하는지도 프로젝트의 목표였다.
- 요구사항 21개 구현은 수정 요약본의 완료 범위다. 사용자 반응이나 업무 개선 효과를 측정했다는 뜻은 아니다.

**예상 발표 시간**: 40초.

**화면 구성 및 전환**

- 중앙에 다섯 단계의 가로 흐름을 배치한다. 발표 중 ‘참여’와 ‘메뉴 취합’을 차례로 강조해 뒤의 사례를 위한 위치만 익히게 한다.
- 텍스트만으로 완결되게 만든다. 실제 화면 캡처가 없어도 설명이 가능하며, 라이브 데모나 영상으로 전환하지 않는다.
- 다섯 단계로 제품 흐름을 익힌 뒤, 6·7장의 공통 규칙·문서를 거쳐 9장의 기능 담당 범위와 연결한다.

**다음 장 연결 멘트**: “앱은 정했습니다. 그다음은 누가 무엇을 할지였는데, 시작은 사다리였습니다.”

**근거**: 수정 요약본 §1·§4, `docs/common/planning.md` §2.

### 4. 역할은 사다리가 정했고, 할 일은 우리가 정했다

**핵심 메시지**

초기 역할 배정 이후 구체적인 책임과 맞물리는 역할은 대화로 조정했다.

**실제 표시할 내용**

> 사다리 결과: 컨텍스트 관리 / 검증·기록 / 통합

> “구체적으로 뭘 해야할지 모르겠어요.. ㅋㅋㅋ” — 손해솔

>

### 5. 초안은 한 사람이, 기준은 함께

**핵심 메시지**

기획 담당자의 부담은 초안 작성뿐 아니라 함께 받아들일 수 있는 판단을 만드는 데 있었다.

**실제 표시할 내용**

> “누군가는 초안을 만들어야 하지만, 모두가 어느 정도 타당하다고 인정할 수 있는 기획이어야 했기 때문에”
> — 민웅기, 프로젝트 회고
>
> 실제 논의: 겸상인데 Host 혼자 메뉴를 골랐다면?
> 결정: 그 이유만으로 자동 취소 조건을 추가하지 않음

**발표자가 설명할 내용**

- 웅기는 기획이 가장 신경 쓰였다고 회고했다. 문서를 먼저 썼다는 절차 설명에 앞서, 합의 가능한 초안을 만드는 일이 있었다는 맥락을 제공한다.

- “이름은 겸상인데 혼자 먹어도 되는가까지 논의했습니다”는 발표용 멘트다. 모든 도메인 규칙을 설명하지 않고 작은 앱에도 함께 정할 판단이 있었다는 사례로 쓴다.
- 회고의 개인 감상을 팀원 전체의 동일한 경험으로 일반화하지 않는다.

**예상 발표 시간**: 60초.

**화면 구성 및 전환**

- 따뜻한 회고 문구와 구체적인 기획 질문을 대비하되, 실제 화면·대화를 새로 만들어 증거처럼 제시하지 않는다.

**다음 장 연결 멘트**: “이렇게 정한 내용을 각자의 AI도 같은 기준으로 읽을 수 있어야 했습니다.”

**근거**: S3 웅기 회고 전문, S2 10월 23일 18:03–18:06 대화.

### 6. 도구는 각자, 규칙은 하나

**핵심 메시지**

서로 다른 도구가 같은 규칙을 읽게 하려 공통 규칙을 한 파일로 모았다.

**실제 표시할 내용**

> 민웅기·손해솔: Claude Code / 유가을: Codex
>
> 공통 규칙: `AGENTS.md`
>
> 규칙 확인 → `TECHDAY-OK`

**발표자가 설명할 내용**

- 도구별 규칙 파일이 갈라지면 같은 작업에도 서로 다른 지시를 따를 수 있어, 공통 규칙은 `AGENTS.md`에만 두고 도구별 설정은 이를 읽게 했다.
- “도구는 달랐지만 규칙을 읽었는지 확인할 때의 대답은 같았습니다. TECHDAY-OK.”
- 확인 응답은 규칙 로딩을 점검하는 약속이다. 이후 행동의 규칙 준수를 보증하지 않는다. 네 도구용 규칙 지원과 실제 사용한 두 도구도 구분한다.

**예상 발표 시간**: 45초.

**화면 구성 및 전환**

- 도구 이름 두 묶음이 같은 규칙 파일을 가리키는 간단한 도식.
- 확인 문구를 한 번 노출하고 ‘규칙 로딩 확인 예시’로 표시한다.

**다음 장 연결 멘트**: “같은 규칙에 더해, 세션이 달라도 다시 읽을 요구사항이 필요했습니다.”

**근거**: 수정 요약본 §5의 AI 도구·규칙 파일, 회고 #1, [규칙 단일화 결정 #11](https://github.com/congsole/tech-day/issues/11).

### 7. 구현 전에 합의부터

**핵심 메시지**

세션을 넘어 같은 맥락을 전달하기 위해, 만들 동작과 구현의 경계를 문서에 남겼다.

**실제 표시할 내용**

> 문서 PR 승인·머지 → 요구사항 이슈 → 구현 PR
>
> 요구사항 ID + Given / When / Then
>
> `[확인 필요]`가 남으면 구현 중단

**발표자가 설명할 내용**

- #7에서는 세션마다 맥락을 다시 전달해야 한다는 문제의식으로 문서를 팀의 공통 기준으로 정했다. 에이전트의 기억 기능에 관한 일반론보다 이 팀이 선택한 전달 방법을 설명한다.

**예상 발표 시간**: 45초.

**화면 구성 및 전환**

**다음 장 연결 멘트**: “그렇게 문서를 기준으로 삼았는데도, 한 사람의 AI에만 남은 결정이 있었습니다.”

### 8. 제 AI는 알고 있었습니다

**핵심 메시지**

개인 작업 맥락에 남은 결정이 다른 사람의 에이전트가 읽을 공통 근거로 이어지지 않은 경험이다.

**실제 표시할 내용**

> 제 AI는 알고 있었습니다
> 다른 사람의 AI는 근거를 찾을 수 없었습니다
>
> Host 넘기기 대기 중 참여 허용
> 개인 작업 맥락 → 공통 결정 근거 전달의 공백
>
> 민웅기의 회고 사례

**발표자가 설명할 내용**

- 웅기의 회고에 따르면 Host 넘기기 대기 중 참여 허용 결정은 자신의 AI에만 남아 있었다. 가을의 에이전트가 참여 기능을 구현할 때 의도된 동작인지 판단할 근거가 없었다.
- 해솔도 PR #123에서 meal·join 요구사항과 화면 설계, 공통 DB 문서에 이 동작을 정한 기록이 없다고 확인했다. 이는 공통 근거가 남지 않았다는 회고와 맞는 정황이며, 결정 당시의 모든 기록이 없었다는 증명은 아니다.
- 문서 중심 작업 방식을 정해 두었어도 결정이나 이유가 모두 공유되지는 않았다고 회고했다. 앞 장의 규칙을 무효로 단정하지 않고 운영 중 생긴 공백으로 설명한다.
- “혼자였다면 제 AI가 기억하고 있으니”는 회고자의 당시 인식이다. AI가 항상 기억한다거나 다른 세션의 기억을 보장한다는 기술적 주장으로 쓰지 않는다.
- 다시 논의하거나 근거를 재추적하는 비용을 느꼈다는 회고를 소개한다. 이 특정 사례의 수정 PR·반영 시점은 아직 대조하지 않았으므로 해결 완료나 재발 방지 성과를 붙이지 않는다.
- 연결할 질문: 한 사람의 결정이 다른 팀원의 에이전트도 읽을 수 있는 위치에 남았는가?

**예상 발표 시간**: 85초.

**화면 구성 및 전환**

- 왼쪽 개인 작업 맥락, 오른쪽 다른 팀원의 구현 작업을 놓고 가운데 공통 근거의 빈칸을 보여준다.
- “근거를 찾을 수 없었다”는 회고 요약임을 표시한다. 실제 AI 응답처럼 꾸미지 않는다.
- 마지막에 기록 위치를 묻는 문장을 드러내며 다음 기능 분담 설명으로 넘어간다.

**다음 장 연결 멘트**: “공통 맥락을 나누는 것과 함께, 실제 구현도 서로 기다리지 않도록 나눴습니다.”

**근거**: S3 웅기 회고 전문의 결정 근거 공유 사례, S7 해솔의 관련 문서 확인 내용. 해당 동작의 결정·반영 이력과 해결 결과는 추가 확인 전까지 주장하지 않는다.

### 9. 기능은 나누고, 자주 합치기

**핵심 메시지**

**실제 표시할 내용**

> 한 명은 다른 곳의 업무 프로젝트, 두 명은 본사에서 각자의 본업
>
> 한참 논의 → 본업 복귀 → 시간 날 때 PR 제출 → 승인 대기
>
> “PR 승인 부탁드립니당” — 손해솔, 10월 13일
>
> 코드를 만드는 시간 말고, 서로 다시 모이는 시간도 필요했다

**발표자가 설명할 내용**

- 가을의 회상에 따르면 한 명은 다른 곳에서 업무 프로젝트를 수행했고, 본사의 두 명도 각자 본업으로 바빴다. 같은 장소에 있는 것과 동시에 이 프로젝트를 볼 수 있는 것은 달랐다.

- 채팅 응답이나 머지 승인에서 누군가 바로 확인하기 어려운 공백이 있었다는 경험을 소개한다. 정확한 빈도·대기 시간·지연 비율은 측정하지 않았으므로 숫자를 붙이지 않는다.

### 12. 문서는 시간 차이를 메웠고, 승인 대기도 만들었다

**핵심 메시지**

문서와 PR의 기록 덕분에 서로 다른 시간에도 협업을 이어갔지만, 기록·브랜치 관리와 승인 대기 역시 작업 부담이 되었다.

**실제 표시할 내용**

> 사람은 잠깐 사라져도, 논의는 PR에 남아 있었다

| 도움이 된 점 | 부담이 된 점 |
|---|---|
| 논의·결정·수정 이력이 남음 | 문서 승인까지 기다리는 구간 |
| 코드 줄을 짚어 버그 가능성 지적 | 문서 전용 브랜치·PR 관리 |
| 돌아와서 맥락을 읽고 검토 재개 | 기록 자체가 별도의 작업이 됨 |

> 다음에 조정할 질문
> 어떤 결정은 승인을 기다리고, 어떤 작업은 기록하며 진행해도 될까?

**발표자가 설명할 내용**

- 가을은 PR 안에서 대화하고 버그 가능성이 있는 코드 줄을 지목해 댓글을 남기는 방식이 효율적인 리뷰에 도움이 됐다고 회고했다. 코드·댓글·수정 이력이 연결돼 늦게 돌아온 사람도 맥락을 읽고 작업을 이어갈 수 있었다.
- 동시에 문서 승인을 기다리거나 문서 전용 브랜치와 PR을 관리하고, 기록을 남기는 일 자체에 부담을 느꼈다. 이는 가을의 경험이며 리뷰 시간 단축률·승인 지연 시간·문서량의 측정 결과는 아니다.
- 문서가 모든 일을 느리게 했다는 설명도, 문서만 있으면 대기가 사라졌다는 설명도 하지 않는다. 기록으로 이어갈 수 있는 작업은 진행됐고, 응답·판단·승인을 기다리는 구간도 남았다는 경험이다.
- 다음에는 공통 스키마·기능 간 동작을 바꾸는 결정과 한 기능 내부의 작은 수정에 같은 무게의 절차가 필요한지 검토해 볼 수 있다. 이 분류는 발표용 개선 질문이며, 이번 프로젝트에서 합의·적용한 새 승인 정책은 아니다.
- PR #104에서는 응답 상자와 겸상 정보 컴포넌트의 특정 줄을 짚어 재응답 가능 구간과 조회 실패 처리 문제를 지적했다. `9fe02a5`에서 두 항목을 수정하고, 모의 API를 사용한 재검증 후 승인한 이력이 이어진다. 발표에서는 ‘줄 단위 지적 → 수정 → 재검증·승인’만 짧게 소개한다. 실환경 검증이나 리뷰 시간 단축의 증거로 확대하지 않는다.

**예상 발표 시간**: 75초.

**화면 구성 및 전환**

### 13. AI들끼리 먼저 얘기하면 안 되나?

**핵심 메시지**

응답·승인을 기다리며 에이전트끼리 먼저 논의하면 더 빠르겠다는 생각이 들었지만, 실제 비교 실험으로 확인한 효과는 아니다.

**실제 표시할 내용**

> AI들끼리 먼저 얘기하면 안 되나?
>
> 가을의 당시 생각: 서로 확인을 기다리는 시간을 줄일 수 있지 않을까
>
> 기대 · 실제 비교 실험 없음

**발표자가 설명할 내용**

- 문서·PR로 비동기 작업을 이어갔지만, 가을은 본업으로 자리를 비우는 사이 응답·판단·승인이 기다리는 순간에는 사람이 병목처럼 느껴졌다고 했다. 이는 협업 대기에 대한 개인의 체감이며, 팀원 능력이나 성실성에 대한 평가는 아니다.
- AI끼리 대화했다면 효율이 더 좋았을 것 같다는 기대를 소개한다. 이 프로젝트에서 자율 에이전트 간 협의를 구현·운영했다거나 시간 절감 효과를 얻었다고 말하지 않는다.
- 초안 대조·검토 의견 교환을 먼저 할 수 있을지와, 사람이 기획을 정하고 승인하는 일은 구분한다. 어떤 부분을 맡기면 대기가 줄어드는지는 다음에 확인해 볼 질문으로 둔다.
- 사람을 승인 과정에서 빼자는 결론이나 새로운 자동화 도입 결정은 내리지 않는다. 웃음 뒤에 남는 실제 협업 고민으로 마무리한다.

**예상 발표 시간**: 35초.

**화면 구성 및 전환**

- 질문 한 문장을 크게 표시하고, 다음 클릭에 ‘기대 · 실제 비교 실험 없음’을 함께 보여준다.
- AI끼리 대화하는 가짜 메시지나 작업 완료 장면을 만들지 않는다. 실제로 도입한 방식처럼 보이는 완료 표시도 넣지 않는다.

### 14. 같은 화면인데, 참여 여부가 다르다

**핵심 메시지**

기능을 나눠 구현해도 여러 섹션이 쓰는 데이터의 갱신은 함께 설계해야 했다.

**실제 표시할 내용**

> 참여 완료
>
> 그런데 공지 띠는 나타나지 않았다
>
> 섹션마다 따로 조회한 참여 여부
> → 공유 데이터는 상위 페이지에서 조회·전달

**발표자가 설명할 내용**

- 20초: 같은 파일의 동시 수정 충돌을 피하려 겸상 상세를 기능별 섹션으로 나눴다(#39). 그 구조에서 여러 섹션이 참여 여부 같은 데이터를 각각 조회했다. 참여 직후 공지 띠가 나타나지 않는 불일치가 생겼다.

### 19. 정한 것과 남은 확인을 함께 기록하기

**핵심 메시지**

선택한 협업 구조, 그때 정하지 않은 부분, 실제 대응과 제안을 함께 정리한다.

**실제 표시할 내용**

> decision: 결정과 이유 / retro: 관찰과 개선 제안

| 정한 구조 | 당시 정하지 않은 부분 | 대응·현재 상태 |
|---|---|---|
| 공통 문서로 맥락 공유 | 개인 결정의 근거 전달 | 회고에서 공유 공백 보고 / 특정 사례 반영 이력 추가 확인 |
| 기능별 섹션 분리 | 섹션 간 공유 데이터 갱신 | 상위 조회·전달 반영(#75) |
| 문서·코드의 같은 검토자 | 표시 데이터 × 구독 대상 대조 | 메뉴 구독 추가 완료 / 대조 방식은 제안 |
| 병렬 개발·작은 PR 통합 | 연관 PR 의존성 확인 절차 | 충돌 해결 / 절차는 제안 |

> 다음 요청 예시: 표시 데이터와 구독 대상, 관련 PR의 선행 머지 조건을 대조해 주세요.
> 제안 · 효과 미확인

**발표자가 설명할 내용**

- 20초: 규칙 파일이 비대해지지 않도록 결정과 이유는 decision에, 관찰과 개선 제안은 retro에 남겼다. 결정 전달 공백 행은 웅기의 회고에 근거한다. 표는 발표를 위해 기록을 다시 정리한 것이며 당시 사용한 추적표가 아니다.
- 30초: 섹션 분리는 유지하면서 공유 데이터 조회를 통합했고, 검토에서 빠진 메뉴 구독은 추가했다. 의존성 사례는 선행 조건이 개별 PR에 적혀 있었어도 확인 절차에서 놓친 문제다. 조건 자체가 없었다고 설명하지 않는다.
- 15초: 하단 요청은 #100·#88의 제안을 풀어 쓴 예시다. 두 회고는 공통 규칙으로 추가하지 않고 관찰 기록으로 종료했으며, 이 요청 방식의 효과도 아직 검증하지 않았다. 머지 차단 사항과 후속 통합 작업을 구분해 달라는 요청도 필요에 따라 덧붙일 수 있다.

### 20. 다시 한다면 — 기준은 명확하게, 절차는 간결하게

**핵심 메시지**

웅기는 기획·규약의 중요성과 명확한 기준을, 가을은 그 기준을 운영하는 기록·승인 절차의 간결함을 강조한다. 해솔은 AI가 빠르게 만든 결과를 사람이 읽고 판단하는 부담을 경험하며, 기계가 확인할 것과 사람이 판단할 것까지 기준에 담고 싶다고 회고했다. 세 관점은 명확한 기준과 간결한 운영을 함께 고민한다.

- 가을은 기록과 줄 단위 리뷰가 시간 차이를 메웠다는 점을 좋게 보면서도, 문서 전용 브랜치·승인 대기·과한 기록의 부담을 느꼈다. 다음에는 영향 범위에 맞춰 기록·승인 절차의 무게를 조절할 수 있을지 질문한다.
- 웅기는 무엇을 만들고 어떤 규칙을 따를지 충분히 정하는 중요성을 말하고, 가을은 정한 내용을 기록·검토·승인하는 운영 단계의 복잡도를 줄이고 싶다는 관점이다. 명확한 기획·규약을 갖추면서 절차를 간결하게 하는 것은 함께 추구할 수 있다. 이를 두 사람이 합의한 구체적인 새 운영 정책으로 제시하지는 않는다.
- 인원이 많아지면 속도가 빨라질 수 있다는 웅기의 마지막 소감도 개인의 기대와 확신이다. 실제 인원 비교 실험 결과로 사용하지 않는다.

- 직접 해 보니 AI가 코드·문서·리뷰 의견을 빠르게 만들수록 그것을 읽고 판단하고 통합 순서를 정할 일이 늘었다. 통합 담당에게 이 부담이 몰렸다는 해솔 자신의 경험을 전한다. 모든 팀에 적용되는 생산성 법칙이나 측정 수치로 제시하지 않는다.
- 구체적인 사례는 PR #102다. 가을의 리뷰에서 삭제 반영 누락을 모의 테스트로 재현했으나 해솔은 지적을 제대로 확인하지 못한 채 머지했다고 회고했다. 첫 운영 배포 #115에 포함됐고 #117에서 후속 수정했다. 15장의 메뉴 구독 추가 및 재연결 결함과 구분해 ‘찾은 문제를 처리까지 이어가는 과정’의 공백으로 설명한다. 운영 사용자 피해나 장애 규모는 주장하지 않는다.
- 해솔은 만드는 데 오래 걸리고 확인은 금방 끝난다는 기존 전제가 AI 협업에서는 맞지 않았고, 변경 크기와 무관하게 같은 절차를 거친 것도 부담이었다고 돌아봤다. 이는 개인이 자신의 설계를 돌아보는 이야기이며 책임 추궁이나 실수에 대한 웃음 소재로 쓰지 않는다.
- 다시 한다면 무엇을 만들지뿐 아니라 기계가 확인할 것과 사람이 판단할 것까지 기준을 세우고, 변경 크기에 맞게 절차를 조절하고 싶다고 했다. 웅기의 기준 명확화와 가을의 절차 간소화를 연결하는 제안이며, 자동 검증 체계를 이미 도입해 효과를 얻었다는 뜻은 아니다.

## 5. Reveal.js 구현 단계에 전달할 연출 원칙

- 화면 비율은 16:9를 가정한다. 한글 산세리프와 충분한 여백을 기본으로 하고, 파일명·확인 문구에만 고정폭 글꼴을 고려한다.
- 흐름은 수평 이동 한 줄로 구성한다. 본편에 수직 하위 슬라이드나 분기 탐색을 넣지 않는다.
- 순차 노출은 발표자의 클릭으로 진행한다. 자동 재생·자동 넘김·반복 애니메이션은 사용하지 않는다.
- 위치가 이어지는 전환은 2→3장처럼 의미상 이어지는 곳에 한정한다. 나머지는 짧은 페이드나 즉시 전환으로 충분하다.
- CSS 애니메이션은 공유 데이터가 한 곳으로 모이는 변화, 확인 항목의 강조처럼 설명을 돕는 곳에만 사용한다. 효과를 제거해도 사실과 관계가 읽혀야 한다.
- 화면은 한 장에 한 메시지를 유지한다. 역할·검증 방식·적용 상태는 비교표를 쓰되, 모든 장을 같은 카드 배열로 만들지 않는다.
- 증거는 간결한 출처 번호와 발표자 노트의 링크로 연결한다. 실제 이슈를 새로 그린 대화창이나 가짜 로그로 재현하지 않는다.
- 화면 캡처를 추가한다면 실제 앱·이슈에서 확보한 이미지만 사용한다. 현재 구성은 캡처 없이 텍스트·도식·표만으로 완결된다.
- 영상, 영상 자리 표시자, 재생 버튼, 라이브 데모는 구성에 포함하지 않는다.
- 이번 문서는 연출 아이디어만 제안한다. HTML·CSS·JavaScript 코드나 Reveal.js 설정은 작성하지 않는다.

## 6. 시간과 흐름 검토

### 시간 합계

- 도입·주제·앱(1–3장): 150초, 2분 30초.
- 역할·기획·공통 맥락(4–8장): 305초, 5분 5초.
- 분담·검토·협업 대기·문서의 효용과 부담·사건·실사용·호칭·머지(9–18장): 580초, 9분 40초.
- 기록·개인 회고·종료(19–21장): 275초, 4분 35초.
- 합계 1,310초(21분 50초) + 현장 여유 40초 = 약 22분 30초. 10분으로 줄이는 것이 목표가 아니며, 20~30분을 채우기 위한 내용도 추가하지 않는다.
- 각 시간은 발화·클릭·호흡을 포함한 계획이다. 완성 대본의 실측 시간이 아니므로 리허설 후 조정한다.

### 흐름 검토

- 1장의 사건은 15장에서 회수한다. 앞부분이 길어졌으므로 15장 시작에 ‘처음 말씀드린 검토 세 번의 사건’이라고 다시 짚는다.
- 2장은 초기 아이디어와 주제 선정 과정, 4장은 채팅의 실제 역할 조정, 5장은 웅기의 회고와 구체적인 기획 대화다. 개인 감상과 팀의 결정을 섞지 않는다.
- 6·7장에서 정한 규칙을 설명하고 8장에서 결정 전달의 공백을 보여준다. 규칙이 처음부터 완벽했거나 아무 효과가 없었다는 양극단으로 결론내리지 않는다.
- 9장의 섹션 분리는 14장의 공유 상태로, 10장의 검토 담당은 15장의 관점 누락으로, 병렬 개발은 18장의 순서 문제로 연결한다.
- 15장의 AI 검토 효용과 16장의 직접 사용 경험을 함께 보여준다. 누가 항상 더 정확하다는 비교를 만들지 않는다.
- 17장은 짧은 호흡 전환이다. 설명이 늘어나면 축약할 수 있지만 사람-AI 협업의 일상적인 느낌은 살린다.
- 19장은 적용·제안을 정리하고, 20장은 기준의 내용·운영 절차·확인과 판단의 분담을 보완하는 세 관점을 들려준다. 21장은 교훈 목록을 반복하지 않고 질문으로 끝낸다.

- 11장은 응답 시간의 차이, 12장은 그 차이를 메운 문서와 절차 부담, 13장은 그래도 대기할 때 떠올린 자동 협의 기대를 보여준다. 모든 협업이 멈췄다는 인상을 피하고, 기대를 실제 효과로 연결하지 않는다.
- 12장에서 나온 승인 범위 질문은 20장의 가을 회고로 이어진다. 웅기의 기획·규약 강조는 내용의 충실함, 가을의 질문은 운영 절차의 간결함에 초점을 둔다는 점을 연결한다.

### 리허설에서 조정할 부분

- 주제 후보는 짧게 소개하고, 다들 볼륨 있는 생각에서 간단한 공동 주제로 정리했다는 흐름에 집중한다.
- 역할 표는 이름·기능을 모두 읽기보다 선택 이유를 중심으로 설명한다.
- 11장의 사라짐 연출은 특정인에게 몰아주지 않고, 해솔의 리마인드는 한 번 짧게 보여준다. 출석 확인이나 책임 추궁처럼 들리는지 점검한다.
- 15장의 검토 관점·실제 수정·개선 제안·검증 방식은 밀도가 높으므로 클릭 구간을 나누고 필요하면 시간을 늘린다.

- 20장은 각자의 직접 인용과 요약을 구분하고, 해솔의 사례를 포함해 시간을 90초 늘렸다. 12장의 장단점 표를 다시 읽지 않으며, #102의 삭제 반영 지적을 15장의 다른 결함과 혼동하지 않도록 한다. 새로운 합의가 이뤄졌다고 표현하지 않는다.
