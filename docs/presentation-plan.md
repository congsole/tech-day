### 중심 메시지

**이 프로젝트에서는 검토를 여러 번 받아도 연결된 부분의 누락을 놓쳤다. 무엇을 함께 확인할지, 어떤 순서로 합칠지를 구체적으로 정하는 일이 남았다.**

AI의 일반적인 능력에 관한 결론이 아니라, 이 팀의 개발 기록에서 관찰한 내용으로 말한다. 공통 문서와 교차 검토가 실제로 어떻게 쓰였는지 보여주고, 그것만으로 해결되지 않았던 문제도 함께 남긴다.

### 청중과 말투

- PR·코드 리뷰 경험이 있는 사내 개발자를 주요 청중으로 가정한다. Supabase나 앱 내부 구조에 대한 사전 지식은 요구하지 않는다.
- 발표자는 한 명, 팀의 경험을 소개할 때는 우리 팀이라는 표현을 쓴다. 개인별 감정이나 당시 대화는 추정하지 않는다.
- 위트는 검토 세 번과 누락 한 개, 같은 화면의 서로 다른 참여 상태, 승인과 머지 순서의 어긋남에서 만든다. 가상의 AI 답변, 팀원 탓, 도구별 우열 비교는 넣지 않는다.
- 사건을 소개할 때는 증상 → 협업 구조와 원인 → 실제 대응 → 남은 점 순서로 말한다. 사례의 제시 순서는 설명을 위한 배열이며 실제 발생 순서를 뜻하지 않는다.

### 비중을 낮추거나 본편에서 제외할 내용

- 기능별 시연, 인증 절차, 전체 기술 스택 설명: 앱 소개 한 장으로 제한한다.
- PR·이슈 총량과 도구별 기능 비교: 발표의 중심 메시지를 설명하는 데 필요하지 않으므로 본편에 넣지 않는다. 집계 정보는 현재 요약본의 2026-11-03 기준을 따른다.
- 개발 시간 단축률, 비용 절감, 사용자 반응, 정산 혼선 감소 성과: 측정 근거가 없으므로 주장하지 않는다. 정산 혼선 감소는 개발 목적이다.
- 상세 DB 구조, 코드 조각, 모든 버그 목록: 협업 문제를 설명하는 데 필요한 구독 대상·공유 데이터·선행 조건만 다룬다.

## 4. 슬라이드별 구성안

### 1. 검토 세 번, 누락 하나

**핵심 메시지**

같은 누락이 세 차례의 AI 검토를 지나갔다. 이 사건을 따라가며 팀의 협업 방식을 살펴본다.

**실제 표시할 내용**

> 검토 세 번, 누락 하나
>
> AI를 활용한 앱 개발 협업기 — 겸상
>
> 다른 참여자의 메뉴 변경이 취합 현황에 반영되지 않았다

**발표자가 설명할 내용**

- “세 사람이 각자 AI와 앱을 만들었습니다. AI 검토도 세 번 있었는데, 다른 사람이 바꾼 메뉴가 화면에 반영되지 않는 누락은 남았습니다.”
- 세 번은 동일한 체크리스트로 반복한 검토가 아니라 서로 다른 관점의 검토였다. 자세한 경위는 6장에서 설명한다.
- “오늘은 이 앱을 만들면서 서로 무엇을 맞췄고, 어디서 어긋났는지 이야기하겠습니다.”

**예상 발표 시간**: 35초. 제목을 읽고 2초 쉬는 시간 포함.

**화면 구성 및 전환**

- 넓은 여백에 제목 한 줄. 먼저 ‘검토 세 번’을 보여주고 클릭 한 번으로 ‘누락 하나’를 강조한다.
- 증상 한 줄은 그다음에 나타낸다. 성공 체크 표시 세 개로 표현하지 않는다. 세 검토가 전체 앱의 통과를 보증한 것처럼 보일 수 있기 때문이다.
- 다음 장에서 같은 ‘겸상’ 글자가 제품 소개의 제목 위치로 이어지도록 전환한다.

**다음 장 연결 멘트**: “먼저, 메뉴가 바뀌어야 했던 이 앱부터 짧게 보여드리겠습니다.”

**근거**: 수정 요약본 §3 ①, [회고 #100](https://github.com/congsole/tech-day/issues/100).

### 2. 겸상: 같이 먹는 앱을 같이 만들기

**핵심 메시지**

제품은 하나의 식사 흐름을 완성하는 범위였고, 프로젝트에는 각자의 AI와 함께 개발하는 협업 실험도 포함됐다.

**실제 표시할 내용**

> 겸상
>
> 같이 먹고, 같이 시키고, 깔끔하게 나누는 사내 식사 모집 웹앱
>
> 겸상 열기 → 참여 → 메뉴 취합 → 주문 → 정산
>
> 핵심 요구사항 21개 구현 · 정산은 금액 표시까지

**발표자가 설명할 내용**

- 메신저로 인원을 모으고 메뉴·금액을 취합하면서 생기는 누락과 정산 혼선을 줄이려는 목적이었다.
- 실제 주문과 송금은 앱 밖에서 한다. 앱의 정산은 각자가 부담할 금액을 보여주는 범위다.
- 세 사람이 각자 에이전트를 사용해 동시에 개발할 때 무엇을 맞춰야 하는지도 프로젝트의 목표였다.
- 요구사항 21개 구현은 수정 요약본의 완료 범위다. 사용자 반응이나 업무 개선 효과를 측정했다는 뜻은 아니다.

**예상 발표 시간**: 40초.

**화면 구성 및 전환**

- 중앙에 다섯 단계의 가로 흐름을 배치한다. 발표 중 ‘참여’와 ‘메뉴 취합’을 차례로 강조해 뒤의 사례를 위한 위치만 익히게 한다.
- 텍스트만으로 완결되게 만든다. 실제 화면 캡처가 없어도 설명이 가능하며, 라이브 데모나 영상으로 전환하지 않는다.
- 다섯 단계를 다음 장의 기능 담당 범위와 연결한다.

**다음 장 연결 멘트**: “이 흐름을 세 사람이 나눠 맡았고, 쓰는 AI도 같지는 않았습니다.”

**근거**: 수정 요약본 §1·§4, `docs/common/planning.md` §2.

### 3. 도구는 각자, 규칙은 하나

**핵심 메시지**

도구는 각자 선택하되, 기능 담당과 공통 역할을 나누고 같은 규칙 파일을 공유했다.

**실제 표시할 내용**

| 사람 · 도구 | 기능 담당 | 공통 역할 |
|---|---|---|
| 민웅기 · Claude Code | 로그인·겸상 열기·목록 | 기획·컨텍스트 |
| 유가을 · Codex | 참여·메뉴·주문 확정 | 검증·기록·디자인 |
| 손해솔 · Claude Code | 주문·정산·공지 | 통합·DB 스키마 |

> 공통 규칙: `AGENTS.md`
>
> 규칙 확인 → `TECHDAY-OK`

**발표자가 설명할 내용**

- 기능은 한 사람이 API부터 화면까지 맡는 방식으로 나눴다. 동시에 기획, 검증, 통합처럼 기능 사이를 연결하는 역할도 따로 두었다.
- 도구별 규칙이 갈라지지 않도록 공통 규칙을 `AGENTS.md`에만 쓰고, 도구별 설정은 이를 읽게 했다.
- “도구는 달랐지만, 규칙을 읽었는지 확인할 때의 대답은 같았습니다. TECHDAY-OK.” 잠깐 쉬어 가는 지점으로 쓴다.
- 이 응답은 규칙 로딩을 점검하는 약속이며, 이후 행동이 모두 규칙을 지켰다는 보증은 아니다.
- 표는 프로젝트의 기능 담당 이력이다. 마무리 기간에는 가을·해솔의 상호 검토로 전환했다는 점은 말로 짧게 덧붙인다.

**예상 발표 시간**: 55초.

**화면 구성 및 전환**

- 세 행을 한 번에 읽을 수 있는 간결한 표. 사람 이름을 먼저 보이게 하고 AI 이름은 같은 행의 보조 정보로 둔다.
- 표 아래 `AGENTS.md`를 보여준 뒤 확인 문구를 한 번 나타낸다. 실제 대화 캡처를 흉내 내지 않고 ‘규칙 로딩 확인 예시’로 표현한다.
- 다음 장에서는 규칙 파일 제목이 문서 기반 작업 흐름의 시작점으로 이어진다.

**다음 장 연결 멘트**: “같은 규칙을 읽게 했다면, 다음은 같은 요구사항을 보고 개발하게 하는 일이었습니다.”

**근거**: 수정 요약본 §2·§5의 AI 도구·규칙 파일·검토 체계, `docs/common/planning.md` §4.

### 4. 구현 전에 합의부터

**핵심 메시지**

요구사항과 승인된 문서를 기준으로 구현을 맡기고, 미정 사항과 사람의 승인 지점을 명시했다.

**실제 표시할 내용**

> 문서 PR 승인·머지 → 요구사항 이슈 → 구현 PR → 사람의 승인·통합
>
> 요구사항 ID + Given / When / Then
>
> `[확인 필요]`가 남으면 구현 중단

**발표자가 설명할 내용**

- 사람들은 먼저 문서로 만들 동작을 합의했다. 에이전트는 요구사항 ID와 인수 조건을 읽고 구현했다.
- 요구사항 이슈에는 문서 경로와 ID를 넣어, 같은 요구사항의 본문이 여러 곳에서 갈라지지 않게 했다.
- 에이전트가 초안 작성·이슈 생성·구현·검토 의견을 맡고, 사람은 초안을 승인하고 PR을 승인·머지·통합했다. 이슈 생성도 초안 승인 후 진행하는 구조였다.
- 미정 부분을 에이전트가 채우게 두지 않고 `[확인 필요]`로 표시했다.
- “여기까지 보면 꽤 질서정연합니다. 그런데 기능을 합친 화면에서는 다른 문제가 나왔습니다.”

**예상 발표 시간**: 55초.

**화면 구성 및 전환**

- 가운데 작업 흐름 한 줄을 둔다. 사람이 승인하는 두 지점을 같은 색으로 강조한다.
- `[확인 필요]` 문구를 보이는 순간 흐름 강조를 멈춰, 미정 상태에서는 진행하지 않는 규칙을 보여준다.
- 다음 장은 문서 흐름에서 화면의 참여·공지 영역으로 컷 전환한다. 규칙을 소개하는 정돈된 화면과 실제 문제의 대비는 시각적으로만 만든다.

**다음 장 연결 멘트**: “참여 기능과 공지 기능을 나눠 만들었더니, 같은 화면 안에서 참여 여부가 달라졌습니다.”

**근거**: 수정 요약본 §5의 문서가 원천·사람과 AI의 역할 경계.

### 5. 같은 화면인데, 참여 여부가 다르다

**핵심 메시지**

기능을 나눠 구현해도 여러 섹션이 쓰는 데이터의 갱신은 함께 설계해야 했다.

**실제 표시할 내용**

> 참여 완료
>
> 그런데 공지 띠는 나타나지 않았다
>
> 섹션마다 따로 조회한 참여 여부
> → 공유 데이터는 상위 페이지에서 조회·전달

**발표자가 설명할 내용**

- 20초: 겸상 상세를 기능별 섹션으로 나누어 구현했고, 여러 섹션이 참여 여부 같은 데이터를 각각 조회했다. 참여 직후 공지 띠가 나타나지 않는 불일치가 생겼다.
- 15초: 참여 섹션에서 행동이 성공해도, 공지 섹션이 별도로 읽은 참여 여부까지 함께 갱신되는 구조는 아니었다. 각 기능의 성공과 화면 전체 상태의 일치가 연결되지 않았다.
- 25초: #75에서 여러 섹션이 공유하는 데이터는 상위 페이지에서 조회·전달하고, 이를 바꾸는 행동 뒤에는 부모에서 다시 조회하도록 결정했다. 통합 담당이 통합 PR에서 반영했다. 섹션 전용 데이터는 해당 섹션이 계속 맡았다.
- 10초: 다른 사용자의 변경을 받는 실시간 구독은 이후 별도로 반영했다. #75에서 실시간 구독까지 함께 확정한 것으로 설명하지 않는다.

**예상 발표 시간**: 70초.

**화면 구성 및 전환**

- 실제 앱 화면을 복제하지 않는 설명용 도식. 왼쪽에 ‘참여’, 오른쪽에 ‘공지’를 놓고, 각자가 읽는 ‘참여 여부’를 각각 표시한다.
- 클릭하면 공통 ‘참여 여부’ 하나가 위쪽에 자리 잡고 양쪽에 전달되는 모습으로 전환한다. ‘개선 전 / 반영한 구조’를 명시한다.
- 별도 조작 없이 두 상태를 비교할 수 있도록 전환 후 핵심 문구를 유지한다. CSS 애니메이션을 쓰더라도 한 번만 재생한다.

**다음 장 연결 멘트**: “공유 데이터를 맞춘 뒤에도, 다른 사람이 바꾼 메뉴까지 들어오게 하려면 확인할 연결이 더 있었습니다.”

**근거**: 수정 요약본 §3 ②, [공지 구현 PR #61](https://github.com/congsole/tech-day/pull/61), [공유 데이터 결정 #75](https://github.com/congsole/tech-day/issues/75).

### 6. 세 번의 검토가 비워 둔 한 칸

**핵심 메시지**

각 검토가 보는 관점이 달랐지만, 화면에 필요한 데이터와 실시간 구독 대상을 전체 대조하는 확인은 빠져 있었다.

**실제 표시할 내용**

> 화면 관점 · 구현 품질 · 문서와 구현 대조
>
> 빠진 확인: 화면의 표시 데이터 × 실시간 구독 대상
>
> 실제 수정: 메뉴 테이블 구독 추가
> 개선 제안: 화면 × 테이블 대조

**발표자가 설명할 내용**

- 20초: 도입의 사건으로 돌아온다. 실시간 구독을 정할 때 메뉴 항목 테이블이 빠졌고, 작성 쪽 에이전트도 결정에 적힌 테이블을 기준으로 구현했다.
- 20초: 검토는 담당 화면, 응답 순서 등 구현 품질, 문서와 구현의 일치 관점으로 진행됐다. 그동안 화면에서 보여주는 데이터가 모두 구독 대상에 들어 있는지는 대조하지 않았다. 문서와 코드가 맞는다는 확인만으로 문서 자체의 누락까지 잡지는 못했다.
- 20초: Host의 취합 현황을 검토하면서 다른 참여자의 메뉴 변경이 반영되지 않는 현상이 확인됐다. #101 결정 후 #102에서 메뉴 테이블 구독을 추가했다.
- 20초: 화면 × 테이블 대조를 검토 요청에 포함하자는 내용은 회고의 개선 제안이다. 실제 적용해 누락 재발을 막았다고 말하지 않는다. “검토가 세 번 있었다는 사실만으로, 빠진 확인이 채워지지는 않았습니다.”

**예상 발표 시간**: 80초. 본편에서 가장 길게 설명하는 대표 사례.

**화면 구성 및 전환**

- 1장의 ‘세 번’ 숫자를 재사용한 뒤 세 검토 관점을 차례로 펼친다. 검토 관점 사이를 서로 연결해 완벽한 망처럼 보이게 만들지 않는다.
- 아래에 ‘표시 데이터 × 구독 대상’이라는 비어 있던 확인 한 줄을 드러낸다. 실제 전수 대조표가 존재한 것처럼 새 표를 증거로 제시하지 않는다.
- 마지막에는 ‘실제 수정’과 ‘개선 제안’을 텍스트로 구분해 동시에 남긴다. 색만으로 상태를 구분하지 않는다.

**다음 장 연결 멘트**: “데이터 연결에서 빠진 확인이 있었다면, PR을 합치는 순서에서도 빠진 확인이 있었습니다.”

**근거**: 수정 요약본 §3 ①·§5의 AI 교차 검토, [회고 #100](https://github.com/congsole/tech-day/issues/100), [구독 추가 PR #102](https://github.com/congsole/tech-day/pull/102).

### 7. 승인됐다고 먼저 머지하면

**핵심 메시지**

개별 PR의 승인 상태와 여러 PR을 합쳐야 하는 순서는 별개였다. 이미 적혀 있던 선행 조건도 놓쳤다.

**실제 표시할 내용**

> 승인 확인 ≠ 머지 순서 확인
>
> #88: 명시된 선행 머지 조건 누락 → 통합 충돌
> #27: 선행 문서 머지 전 분기 → 스키마와 기획 불일치
>
> 충돌 해결: 통합 담당
> 의존 PR 확인 절차: 규칙화하지 못한 과제

**발표자가 설명할 내용**

- 25초: #88에서는 #80에 선행 머지와 통합 절차가 적혀 있었다. 에이전트는 #71·#72 각각의 승인 상태와 머지 가능 여부를 보고 안내했고, 이들이 먼저 머지된 뒤 #80에서 충돌이 발생했다. 요구된 순서는 #80이 먼저였다.
- 15초: 별개의 앞선 사례인 #27에서는 공통 문서 변경이 반영되기 전에 DB 스키마 브랜치를 따서, 주문중 상태 변경이 빠진 채 기획과 스키마가 어긋났다. 두 사건이 같은 날 연속으로 발생했다고 말하지 않는다.
- 15초: 통합 담당이 충돌을 해결했다. 연관 PR 의존성 확인과 선행 조건 교차 링크는 개선 방향으로 남았으며 마무리 기간에 규칙화하지 못했다.
- 10초: “이 경우는 AI가 전달받지 못한 정보를 추측해야 했던 문제가 아닙니다. 적혀 있던 순서도 확인에서 빠졌습니다.”

**예상 발표 시간**: 65초.

**화면 구성 및 전환**

- 첫 화면에 ‘승인’과 ‘순서’를 큰 글자로 나란히 둔다.
- #88을 설명할 때 ‘지정된 순서: #80 → #71·#72’와 ‘실제 선행 머지: #71·#72’를 두 줄로 보여준다. 둘의 차이를 수동 클릭으로 강조한다.
- #27은 아래의 짧은 별도 사례로만 추가한다. 복잡한 Git 그래프나 충돌 코드 화면은 쓰지 않는다.
- 마지막에는 해결된 충돌과 남은 절차를 함께 보이게 한다.

**다음 장 연결 멘트**: “그렇다고 교차 검토가 소용없었던 것은 아닙니다. 검토 덕분에 발견한 결함도 분명히 있었습니다.”

**근거**: 수정 요약본 §3 ③, [머지 순서 회고 #88](https://github.com/congsole/tech-day/issues/88), [문서 변경 시점 회고 #27](https://github.com/congsole/tech-day/issues/27).

### 8. 교차 검토가 잡아낸 것도 있었다

**핵심 메시지**

다른 사람의 AI가 구현을 검토하며 결함을 찾았고, 문제에 맞는 방법으로 재현해 확인했다.

**실제 표시할 내용**

| 검토에서 찾은 문제 | 확인 방식 |
|---|---|
| 늦은 응답이 최신 상태를 덮음 | 모의 테스트로 응답 순서 제어 |
| 재연결 중 변경 누락 | 실제 Supabase에서도 재현·수정 확인 |

> 작성자 외의 에이전트가 검토 → 사람이 승인·통합

**발표자가 설명할 내용**

- 15초: 작성자의 에이전트만 검토한 것이 아니라, 다른 팀원이 자신의 에이전트로 문서와 구현을 대조했다. 교차 검토에서 실제 결함이 발견됐다.
- 20초: 응답 도착 순서를 바꿔야 하는 문제에는 모의 테스트를 사용했고, 재연결 중 변경 누락은 실제 Supabase에서도 확인했다. 두 방식의 검증 범위는 구분한다.
- 15초: 이 경험에서 확인한 효용은 구체적인 결함의 발견과 재현이다. 모든 검토가 누락을 막았다고 확대하지 않는다. 사람이 승인과 통합을 맡는 흐름도 유지했다.

**예상 발표 시간**: 50초.

**화면 구성 및 전환**

- 문제와 검증 방식을 연결하는 두 행의 표로 충분하다. 코드·로그·DB 화면을 추가하지 않는다.
- 첫 행을 설명한 뒤 두 번째 행을 밝게 표시한다. 두 행 모두 최종 상태에서 남겨 검증 방식의 차이가 보이게 한다.
- 다음 장의 기록 이야기로 넘어갈 때 표의 두 행을 억지로 성공 수치로 변환하지 않는다.

**다음 장 연결 멘트**: “잡아낸 결함도, 끝내 절차로 만들지 못한 제안도 기록에 남겼습니다.”

**근거**: 수정 요약본 §5의 AI 교차 검토, #116 검토 반영 사항 1번.

### 9. 고친 일과 남은 일을 따로 기록했다

**핵심 메시지**

결정의 이유와 회고를 이슈로 남겨, 다음 사람이 적용된 것과 아직 제안인 것을 구분할 수 있게 했다.

**실제 표시할 내용**

> 규칙 파일에는 결정 · decision에는 이유 · retro에는 관찰과 개선 제안

| 적용한 변경 | 개선 제안으로 남은 것 |
|---|---|
| 공유 데이터 조회 통합 | 화면 × 테이블 대조 |
| 메뉴 테이블 구독 추가 | 연관 PR 의존성 확인 절차 |

**발표자가 설명할 내용**

- 규칙 파일에 이유까지 전부 적으면 파일이 커지고, 이유를 빼면 왜 정했는지 사라졌다. 그래서 결정·이유는 decision 이슈에, AI 협업과 검증 과정의 관찰은 retro에 남겼다.
- 표는 이번 발표를 위해 기록을 다시 정리한 것이다. 당시부터 이 표로 추적했다고 설명하지 않는다.
- “지금 고친 것과 다음에 하자는 것을 같은 완료 목록에 넣지는 않겠습니다.”
- #100과 #88의 개선 제안은 마무리 기간에 공통 규칙으로 추가하지 않고 관찰 기록으로 종료했다. 여기에 해결 완료 표시를 붙이지 않는다.

**예상 발표 시간**: 45초.

**화면 구성 및 전환**

- 위에는 기록 위치 한 줄, 아래에는 두 열 비교표. 장식용 카드나 대시보드로 만들지 않는다.
- 실제 반영 사항은 한 번에, 개선 제안은 다음 클릭에 나타내어 상태 차이를 읽게 한다.
- 다음 장에서는 개선 제안 중 하나를 검토 요청 문구로 구체화한다.

**다음 장 연결 멘트**: “이 기록을 다음 작업에 가져간다면, 검토 요청부터 이렇게 바꿔볼 수 있습니다.”

**근거**: 수정 요약본 §5의 협업 기록과 구조, [#100 종료 댓글](https://github.com/congsole/tech-day/issues/100#issuecomment-6516532520), [#88 종료 댓글](https://github.com/congsole/tech-day/issues/88#issuecomment-6516531510).

### 10. 다음 검토 요청에는 연결 관계까지

**핵심 메시지**

회고의 개선 제안을, 검토자가 무엇을 대조해야 하는지 드러나는 요청으로 바꿔본다.

**실제 표시할 내용**

> 다음 작업에 제안하는 검토 요청
>
> 이 화면이 표시하는 데이터와 구독 대상을 대조해 주세요.
> 관련 PR의 선행 머지 조건을 확인해 주세요.
> 머지 차단 사항과 후속 통합 작업을 구분해 주세요.
>
> 회고를 바탕으로 작성한 예시 · 효과는 아직 확인하지 않음

**발표자가 설명할 내용**

- 이 문구는 당시 사용한 프롬프트의 인용이 아니라, #100·#88의 개선 제안을 발표용으로 풀어 쓴 다음 작업의 예시다.
- 메뉴 변경이 필요한 화면과 구독 대상, 각 PR과 선행 조건처럼 실제로 어긋났던 연결을 검토 항목에 넣는다.
- 사람이 모든 코드를 다시 읽어야 한다는 일반론으로 마무리하지 않는다. 이번에 빠졌던 대조 항목을 검토 요청에 명시하자는 정도로 한정한다.
- 아직 이 방식의 효과를 검증한 결과는 없다. 다음 프로젝트에서 적용해 확인할 항목으로 남긴다.

**예상 발표 시간**: 45초.

**화면 구성 및 전환**

- 넓은 화면에 요청 문장 세 줄을 차례로 나타낸다. ‘데이터와 구독 대상’, ‘선행 머지 조건’, ‘차단 사항과 후속 작업’을 각각 강조한다.
- ‘제안’과 ‘효과 미확인’ 표시는 처음부터 유지한다. 실제 에이전트 대화창처럼 꾸미지 않는다.
- 다음 장은 전환 효과를 줄이고 짧은 마무리 문장으로 정리한다.

**다음 장 연결 멘트**: “앱의 핵심 흐름은 구현했고, 협업 방식에는 이렇게 다음에 확인할 일이 남았습니다.”

**근거**: 수정 요약본 §5의 배운 것, #100·#88 개선 제안. 화면 문구는 제안의 재서술이다.

### 11. 겸상, 그리고 남은 질문

**핵심 메시지**

구현된 결과물과 협업에서 남은 질문을 함께 보여주며 마친다.

**실제 표시할 내용**

> 겸상 — 함께 확인할 연결이 남았다
>
> 여러분 팀에서는 PR 사이의 순서를 누가 확인하나요?
>
> 앱: tech-day-nu.vercel.app
> 개발 기록: github.com/congsole/tech-day

**발표자가 설명할 내용**

- “핵심 요구사항은 구현했습니다. 공유 데이터를 합치고 구독 누락도 고쳤지만, PR 의존성을 확인하는 절차까지 모두 정리하지는 못했습니다.”
- “다음에는 검토 횟수뿐 아니라 무엇을 대조했는지도 남겨보려 합니다.”
- 청중에게 화면의 질문을 남긴 뒤 감사 인사로 끝낸다. 본편 안에서 답변을 받는 진행은 하지 않는다.

**예상 발표 시간**: 30초. 마지막 질문을 읽는 호흡과 감사 인사 포함.

**화면 구성 및 전환**

- 제목과 질문에 대부분의 면적을 쓰고 하단에 앱·저장소 링크를 둔다. 질문은 정답이나 교훈이 아니라 대화를 여는 문장으로 표현한다.
- 링크는 구현 시 클릭할 수 있게 하되 본편 중 접속하지 않는다. 이 화면을 유지한 채 종료한다.

**근거**: 수정 요약본 §3·§4·§5. 청중 질문은 발표용 문구다.

## 5. Reveal.js 구현 단계에 전달할 연출 원칙

- 화면 비율은 16:9를 가정한다. 한글 산세리프와 충분한 여백을 기본으로 하고, 파일명·확인 문구에만 고정폭 글꼴을 고려한다.
- 흐름은 수평 이동 한 줄로 구성한다. 10분 본편에 수직 하위 슬라이드나 분기 탐색을 넣지 않는다.
- 순차 노출은 발표자의 클릭으로 진행한다. 자동 재생·자동 넘김·반복 애니메이션은 사용하지 않는다.
- 위치가 이어지는 전환은 1→2장, 3→4장처럼 의미상 이어지는 곳에 한정한다. 나머지는 짧은 페이드나 즉시 전환으로 충분하다.
- CSS 애니메이션은 공유 데이터가 한 곳으로 모이는 변화, 확인 항목의 강조처럼 설명을 돕는 곳에만 사용한다. 효과를 제거해도 사실과 관계가 읽혀야 한다.
- 화면은 한 장에 한 메시지를 유지한다. 역할·검증 방식·적용 상태는 비교표를 쓰되, 모든 장을 같은 카드 배열로 만들지 않는다.
- 증거는 간결한 출처 번호와 발표자 노트의 링크로 연결한다. 실제 이슈를 새로 그린 대화창이나 가짜 로그로 재현하지 않는다.
- 화면 캡처를 추가한다면 실제 앱·이슈에서 확보한 이미지만 사용한다. 현재 구성은 캡처 없이 텍스트·도식·표만으로 완결된다.
- 영상, 영상 자리 표시자, 재생 버튼, 라이브 데모는 구성에 포함하지 않는다.
- 이번 문서는 연출 아이디어만 제안한다. HTML·CSS·JavaScript 코드나 Reveal.js 설정은 작성하지 않는다.

## 6. 시간과 흐름 검토

### 시간 합계

- 도입·앱·협업 구조·작업 규칙(1–4장): 185초, 3분 5초.
- 실제 시행착오 세 사례(5–7장): 215초, 3분 35초.
- 검토 효용·기록·다음 요청·종료(8–11장): 170초, 2분 50초.
- 본편 합계: 570초, 9분 30초. 현장 여유 30초를 더해 10분으로 계획한다.
- 각 장의 시간은 발화, 클릭, 짧은 정지를 포함한 편성 목표다. 발표자 설명은 말할 내용의 가이드이며 완성 대본이 아니므로, 실제 발화 시간은 리허설에서 확인해야 한다.

### 흐름 검토

- 1장은 누락의 존재만 제시하고 6장에서 원인과 대응을 설명한다. 같은 사건을 두 번 길게 설명하지 않는다.
- 2장만 제품 소개에 40초를 사용하고, 이후에는 앱의 기능을 협업 사례를 이해하는 데 필요한 만큼만 언급한다.
- 3장에서 사람의 역할을 먼저 제시해, 5장의 공유 데이터 통합과 7장의 충돌 해결을 누가 맡았는지 자연스럽게 연결한다.
- 4장의 문서 기반 작업 방식은 뒤의 사건을 모두 예방했다는 근거가 아니다. 6장에서는 문서에도 누락이 있었고, 7장에서는 적힌 조건을 놓쳤다는 서로 다른 한계를 보여준다.
- 5–7장은 공유 상태, 검토 범위, 작업 순서라는 다른 문제를 다룬다. 모두 AI가 범위 밖을 보지 못했다는 한 원인으로 뭉뚱그리지 않는다.
- 8장은 결함 발견과 재현이라는 검토의 효용을 보충한다. 앞의 실패를 상쇄하기 위한 성공담을 덧붙이지 않는다.
- 9장은 기록의 상태를 확인하고, 10장은 다음 요청 예시를 제시한다. 11장에서 교훈 목록을 다시 읽지 않고 질문 하나로 마친다.

### 리허설에서 시간을 넘길 경우

1. 3장의 역할 설명을 행별로 읽지 않고 기능 분담·공통 역할의 구조만 설명해 약 10초 축소.
2. 4장에서 요구사항 이슈 본문 형식 설명을 줄여 약 10초 축소.
3. 7장의 #27 사례를 한 문장으로 줄여 약 10초 축소. #88의 명시된 선행 조건 누락은 유지.
4. 6장의 실제 수정과 개선 제안 구분, 8장의 모의·실환경 검증 구분은 시간 조정 시에도 유지.

### 구성안에서 우선 검토할 선택

- 검토 세 번의 누락으로 시작하는 도입이 원하는 분위기에 맞는지.
- 세 사례를 모두 유지할지, 특히 강조하고 싶은 실제 경험이 있는지.
- 마지막을 일반적인 교훈 대신 PR 순서에 관한 질문으로 마치는 방식이 적절한지.

위 선택은 발표 구성에 대한 검토 항목이다. 제품 기획이나 공통 개발 규칙의 변경 제안으로 취급하지 않는다.
